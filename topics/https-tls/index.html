HTTPS / TLS 1.3ClientHello から Finished まで、バイトと鍵の流れを実物で

curl -v https://example.com/ を打ってから最初の GET / が暗号化されて出ていくまでに、回線上では平文の ClientHello / ServerHello と、暗号化されたハンドシェイクメッセージが流れます。このページでは openssl s_client -trace と curl -v の実測出力をもとに、どのバイトが平文で見え、どこで鍵が決まり、クライアントが何をどの順に検証しているのかをステップ再生で追います。

HTTPS は「TCP の上に TLS を張り、その中で HTTP を話す」だけです。TLS 1.3 のフルハンドシェイクは 1-RTT：クライアントが ClientHello を送り、サーバーが ServerHello〜Finished をまとめて返した時点で、クライアントは自分の Finished と一緒に最初の HTTP リクエストを送れます。下のシーンの端末出力は Ubuntu 24.04 の curl 8.5.0 (OpenSSL 3.0.13) で 2026-09 に実測したものです（IP アドレスだけ RFC 5737 の例示アドレスに置き換えています）。

TLS 1.3 の cipher suite は「AEAD と HKDF のハッシュ」だけを決めます。鍵交換（key_share）と署名方式（signature_algorithms）は別々の拡張で交渉します。

ServerHello 以降：鍵スケジュールと暗号化の境界

セッション再開（PSK）と 0-RTT

ハンドシェイク完了後、サーバーは NewSessionTicket を（application key で暗号化して）送ります。次回の接続でクライアントがそのチケットを pre_shared_key 拡張に入れると、サーバーは Certificate と CertificateVerify を省略できます。さらにチケットが early_data を許可していれば、ClientHello と同時にリクエストを送る 0-RTT も可能ですが、リプレイに弱いという代償があります。

0-RTT はリプレイされうる：early data は前回の PSK だけで暗号化され、サーバーのその回の乱数に依存しません。経路上の攻撃者が ClientHello＋early data を録画して再送すると、サーバーは同じリクエストをもう一度処理しかねません（RFC 8446 §8）。POST など冪等でない操作には使わず、nginx なら ssl_early_data on; と proxy_set_header Early-Data $ssl_early_data; を組み合わせ、アプリ側で 425 Too Early（RFC 8470）を返せるようにします。

失敗・攻撃ケース：MITM はどこで止まるか

公衆 Wi-Fi の偽アクセスポイントなど、攻撃者が経路の途中にいる場合を考えます。攻撃者は TCP を横取りでき、ECDHE も自分と成立させられます（鍵交換だけでは相手が誰かは分からない）。それでも接続が止まるのは、証明書チェーン・ホスト名・CertificateVerify の 3 つの検証があるからです。端末出力は curl 8.5.0 / OpenSSL 3.0.13 の実測です。自己署名（A）は手元の openssl s_server -tls1_3 でそのまま再現、ホスト名不一致（C）と -k は badssl.com（TLS 1.2 で応答する）で再現したため、ホスト名とプロトコル表記だけ置き換えています。B（秘密鍵なしの CertificateVerify）は手元で再現できないため、RFC 8446 が定める動作を示します。

curl が表示する alert 番号（560 など）は「level × 256 + description」です。560 = 2(fatal) × 256 + 48(unknown_ca)、557 = 2 × 256 + 45、256 = 1(warning) × 256 + 0(close_notify)。

-k / --insecure は「暗号化はするが、相手が誰かは確かめない」モードです。証明書チェーン・期限・ホスト名の検証をすべてスキップするので、上の MITM A〜C はすべて素通りします（curl 8.5.0 の実測では SSL certificate verify result: self-signed certificate (18), continuing anyway. と 1 行出るだけ）。その結果、Authorization ヘッダや Cookie は攻撃者に復号されます。検証用の自己署名証明書を使うときは -k ではなく --cacert mitm.crt のようにその証明書だけを信頼してください。

設定例（全文）

server {
    listen 443 ssl;
    listen [::]:443 ssl;
    http2 on;                                  # nginx 1.25.1 以降の書き方
    server_name example.com;

    ssl_certificate     /etc/letsencrypt/live/example.com/fullchain.pem;   # leaf → 中間の順
    ssl_certificate_key /etc/letsencrypt/live/example.com/privkey.pem;

    ssl_protocols TLSv1.2 TLSv1.3;             # nginx 1.23.4 以降はこれが既定値
    ssl_ecdh_curve X25519:prime256v1:secp384r1;
    # TLS 1.3 の cipher suite は ssl_ciphers では変わらない（OpenSSL の仕様）
    ssl_conf_command Ciphersuites TLS_AES_256_GCM_SHA384:TLS_CHACHA20_POLY1305_SHA256:TLS_AES_128_GCM_SHA256;

    ssl_session_cache   shared:SSL:10m;
    ssl_session_timeout 1d;
    ssl_early_data      off;                   # 0-RTT。on にするなら Early-Data ヘッダで後段に伝える

    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Early-Data $ssl_early_data;
    }
}
  • ssl_certificate にはサーバー証明書 → 中間証明書の順に連結したファイルを指定します（nginx 公式ドキュメント）。cert.pem を指定すると中間が欠け、curl や Java など AIA で補完しないクライアントだけが失敗します。
  • ssl_conf_command は nginx 1.19.4 以降。ssl_ciphers は TLS 1.2 以下の cipher にだけ効きます（OpenSSL の SSL_CTX_set_cipher_list() は TLS 1.3 に影響しない）。
  • 変数 $ssl_protocol・$ssl_cipher・$ssl_curve（1.21.5+）・$ssl_early_data をアクセスログに入れると、実際に何が交渉されたかを記録できます。

ハマりどころ

ブラウザでは開けるのに curl だけ失敗する
  • ほぼ確実に中間証明書の送り忘れです（ssl_certificate に cert.pem を指定）。ブラウザは AIA による取得やキャッシュで中間を補えることがあるため気付きにくく、openssl s_client -showcerts で送られている枚数を確認します。
openssl s_client は検証に失敗しても接続を続ける
  • Verify return code: 20 (…) と出ても、そのまま HTTP を打ててしまいます。スクリプトでは -verify_return_error を付け、ホスト名も確かめるなら -verify_hostname example.com も付けます。
IP アドレスで接続すると別の証明書が返る
  • openssl s_client -connect 203.0.113.10:443 は SNI を送らないため、nginx は default_server の証明書を返します。-servername example.com を付けるか、curl なら --resolve を使います。
ssl_ciphers を絞っても TLS 1.3 の suite は変わらない
  • OpenSSL では TLS 1.3 の suite は別 API です。nginx は ssl_conf_command Ciphersuites …、curl は --tls13-ciphers、s_client は -ciphersuites を使います。
SNI は平文、ALPN の候補も平文
  • 通信内容は暗号化されても、どのホスト名に接続したかは ClientHello の server_name で経路上から見えます。隠すには ECH（RFC 9849）が必要で、サーバー側が DNS の HTTPS レコードで ECH 設定を公開している必要があります。
時計のずれで「期限切れ」「まだ有効でない」
  • 有効期間の判定はクライアントのローカル時計です。起動直後の組み込み機器や VM で NTP が合っていないと、正しい証明書でも certificate has expired / certificate is not yet valid になります。
証明書を更新したのに古い証明書が返る
  • nginx はファイルを起動時・reload 時にしか読みません。certbot の webroot / standalone 方式では --deploy-hook "systemctl reload nginx" を設定します。
Wireshark で復号できない
  • 鍵ログはクライアント側のファイルです。キャプチャの ClientHello と同じ client_random の行が無ければ復号されません（別の curl、Schannel 版 curl、ブラウザの別プロセスなど）。また TCP の途中から録ったキャプチャではハンドシェイクが無く復号できません。
