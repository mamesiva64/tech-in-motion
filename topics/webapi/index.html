    access_log /var/log/nginx/api.access.log api;

    location /v1/ {
        proxy_pass http://app;                 # URI なし → /v1/users/42 のまま転送
        proxy_http_version 1.1;                # upstream keepalive 用
        proxy_set_header Connection "";
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-Request-ID      $request_id;
        proxy_hide_header X-Powered-By;
        add_header X-Request-ID $request_id always;
        proxy_read_timeout 30s;

location /api/ と proxy_pass の末尾スラッシュ：location /api/ { proxy_pass http://app/; } のように proxy_pass に URI（末尾の / も URI）を書くと、/api/v1/users/42 の /api/ 部分が / に置き換わり、アプリには /v1/users/42 が届きます。proxy_pass http://app;（URI なし）ならパスはそのまま /api/v1/users/42 です。アプリが返す Location: /v1/users/43 のような相対パスは、クライアントから見ると /api が抜けて壊れる点にも注意します。

エラー表現：application/problem+json（RFC 9457）

エラーを API ごとの独自 JSON にせず、Content-Type: application/problem+json と決まったメンバーで返すと、クライアントは共通の処理を書けます。RFC 9457 は RFC 7807 を置き換えた現行仕様です。

メンバー型意味例
typeURI 参照問題の種類の識別子。省略時は "about:blank"（ステータスコード以上の意味はない）"https://api.example.com/problems/validation-error"
title文字列種類の短い要約。同じ type なら毎回同じ文言"Your request is not valid."
status数値HTTP ステータスコードの写し（参考値。実際のステータス行が正）422
detail文字列この発生に固有の説明。人間向けで、パースさせない"User 144 does not exist"
instanceURI 参照この発生を指す URI（リクエストパスやエラー ID）"/v1/users/144"
拡張メンバー任意type ごとに定義してよい追加情報"errors": [{"detail": …, "pointer": "#/email"}]

Idempotency-Key は IETF の Internet-Draft（draft-ietf-httpapi-idempotency-key-header、最新は -07）で、まだ RFC ではありません。値は Structured Field の String（ダブルクォート付き）で、UUID の利用が推奨されています。上表のステータスはドラフトの記述（SHOULD）です。同じく RateLimit-Policy / RateLimit ヘッダ（例：RateLimit: "default";r=0;t=30）も draft-ietf-httpapi-ratelimit-headers（-11）の段階で、実運用では X-RateLimit-Remaining のような独自ヘッダもよく見かけます。
async function withRetry(doFetch, max = 4) {
  for (let attempt = 0; ; attempt++) {
    const res = await doFetch();
    if (![429, 503].includes(res.status) || attempt === max) return res;
    const ra = res.headers.get('Retry-After');            // "30" または HTTP-date
    let sec = ra == null ? NaN : /^\d+$/.test(ra) ? Number(ra) : (Date.parse(ra) - Date.now()) / 1000;
    if (!(sec >= 0)) sec = 2 ** attempt + Math.random();   // 指定がなければ指数バックオフ + ジッタ
    await new Promise((r) => setTimeout(r, sec * 1000));
  }
}

ハマりどころ

動詞の URL：POST /v1/createUser、GET /v1/deleteUser?id=42 は、メソッドの意味（safe / idempotent）とキャッシュ・リトライの前提を壊します。特に GET で削除すると、クローラやプリフェッチが踏んだだけで消えます。
200 でエラーを返す：監視・リトライ・res.ok がすべて「成功」と判定します。失敗はステータスコード＋ problem+json。
オフセットページングの重複・欠落：1 ページ目を読んだ後に先頭へ 1 件追加されると、2 ページ目の先頭が 1 ページ目の末尾と重複します。並び順のキーが一意でない（ORDER BY created_at だけ）と、同じ時刻の行がページ間で入れ替わります。ORDER BY created_at, id のように一意にし、可能ならカーソル方式にします。
日時の形式とタイムゾーン：JSON には RFC 3339（2026-09-28T03:00:00Z や 2026-09-28T12:00:00+09:00）で、オフセット付きで入れます。"2026/09/28 12:00" のようなタイムゾーン不明の文字列や、ミリ秒か秒か分からない数値は避けます。PostgreSQL は timestamptz を使います。
PostgreSQL の bigint が文字列になる：node-postgres は int8 を精度を失わないよう既定で文字列として返すため、"id":"42" と "id":42 が混在しがちです。スキーマ（type: integer / string）と実装を揃えます。
proxy_set_header の継承：nginx では location 内に 1 つでも proxy_set_header を書くと、上位（server / http）で書いた proxy_set_header は引き継がれません。Host を書き忘れるとアプリには Host: 127.0.0.1:3000 相当が届き、絶対 URL の生成を誤ります。
API キーをクエリに入れる：?api_key=… は nginx の access.log、ブラウザ履歴、Referer に残ります。ヘッダで送り、サーバーはハッシュで保存・照合します。
POST の自動リトライ：タイムアウト＝失敗とは限りません（サーバーは処理済みで応答だけ失われたのかもしれない）。Idempotency-Key なしで POST を再送すると二重作成になります。
