Auth · OAuth 2.0 / OpenID Connect

OAuth 2.0 / OIDC認可コード + PKCE を、リダイレクトとトークン交換のパラメータ単位で

「Google でログイン」の裏では、ブラウザが 2 回リダイレクトされ、Web アプリのサーバーが IdP の /token を直接叩いています。 どのパラメータがブラウザ経由（フロントチャネル）で運ばれ、どれがサーバー間（バックチャネル）でしか流れないのか。 state・code_verifier・nonce がそれぞれどの攻撃を防ぐのか。実際の HTTP メッセージで追います。

フロントチャネルブラウザの 302 で運ぶ /authorize?… と redirect_uri?code=…&state=…
バックチャネルClient → AS の POST /token（クライアント認証 + code_verifier）
検証する値state / PKCE S256 / id_token の署名・iss・aud・exp・nonce
仕様RFC 6749 / 6750 / 7636 / 9700・OpenID Connect Core 1.0

登場人物と実エンドポイント

OAuth 2.0（RFC 6749 §1.1）の登場人物は 4 つです。OpenID Connect（OIDC）は OAuth 2.0 の上に「誰がログインしたか」を表す id_token を足した仕様で、 Authorization Server は OIDC では OpenID Provider（OP）、Client は Relying Party（RP）とも呼ばれます。エンドポイントの URL は /.well-known/openid-configuration（OIDC Discovery）から機械的に取得できます。

Discovery 文書のうち、issuer・authorization_endpoint・token_endpoint・jwks_uri・response_types_supported・subject_types_supported・id_token_signing_alg_values_supported は OIDC Discovery 1.0 で必須です（token_endpoint は Implicit のみの OP を除く）。code_challenge_methods_supported は RFC 8414（OAuth 2.0 Authorization Server Metadata）で定義された項目です。

issuer は完全一致で使います。Discovery を取得した URL（/.well-known/openid-configuration を除いた部分）、文書中の issuer、id_token の iss は同一でなければなりません（末尾 / の有無も区別）。

トークン種別の比較

        

          

            
トークン誰が検証する形式送り先 / 用途寿命の目安

            
              
access_tokenResource Server（API）AS 次第：opaque 文字列、または JWT（RFC 9068 の typ: at+jwt）Authorization: Bearer … で API へ。Client は中身を見ない分〜1 時間程度（expires_in）

              
refresh_tokenAuthorization Server多くは opaquePOST /token（grant_type=refresh_token）でのみ使う。API には送らない長め。ローテーションや失効あり

              
id_tokenClient（RP）必ず JWT（JWS）「誰がいつどう認証したか」を Client に伝える。API の認可に使わない短命（受け取った直後に検証するだけ）

            
          

        

        
id_token の検証項目（OIDC Core §3.1.3.7 より主要なもの）

        

          

            
項目比較する値失敗したら

            
              
issDiscovery の issuer と完全一致拒否（別の IdP のトークン）

              
aud自分の client_id を含む（複数なら azp も確認）拒否（他のアプリ宛てのトークン）

              
署名 / algkid で jwks_uri の鍵を選び、想定した alg（既定 RS256）で検証。none は拒否拒否（改ざん・偽造）

              
exp / iat現在時刻 < exp。iat が古すぎないか拒否（期限切れ・再利用）

              
nonce認可リクエストで送り、セッションに保存した値と一致拒否（リプレイ・注入）

              
auth_time / acrmax_age や acr_values を要求した場合に確認再認証を要求

            
          

        

        

          OIDC Core では、Client が TLS でトークンエンドポイントから直接受け取った id_token については、署名検証の代わりに TLS サーバー検証で発行者を確かめてもよい（MAY）とされています。ただしライブラリは通常署名も検証しますし、フロントチャネルで受け取る id_token（Implicit / Hybrid）は必ず署名検証が必要です。

error返る場所典型的な原因

            
              
invalid_request認可 / トークン必須パラメータ欠落、重複、形式不正（code_challenge 必須の AS で欠落など）

              
invalid_clientトークン（400 または 401）クライアント認証失敗（client_secret 誤り、認証方式の不一致）

              
invalid_grantトークンcode の期限切れ・再利用・別クライアント発行、redirect_uri 不一致、code_verifier 不一致、refresh_token 失効

              
unauthorized_client認可 / トークンそのクライアントに許可されていない grant / response_type

              
unsupported_grant_typeトークンAS が対応していない grant_type

              
unsupported_response_type認可AS が対応していない response_type（例：token）

              
invalid_scope認可 / トークン未知・過大なスコープ

              
access_denied認可ユーザーが同意を拒否

              
server_error / temporarily_unavailable認可AS 側の障害（リダイレクトで伝えるための専用コード）

              
invalid_token（RFC 6750）API の WWW-Authenticate（401）access_token の期限切れ・失効・不正

              
insufficient_scope（RFC 6750）API の WWW-Authenticate（403）スコープ不足

            
          

        

        

          redirect_uri が登録値と一致しない認可リクエストに対して、AS はそのリダイレクト先へエラーを返してはいけません（RFC 6749 §4.1.2.1：ユーザーにエラーを表示し、自動リダイレクトしない）。
          一致判定は完全一致の文字列比較です（RFC 9700 §2.1。例外はネイティブアプリの localhost のポート番号のみ）。

grant / response_type使う場面トークン要求の要点現在の扱い

            
              
authorization_code + PKCEWeb アプリ、SPA、モバイル／デスクトップアプリ（ユーザーあり）code + redirect_uri + code_verifier推奨。公開クライアントは PKCE 必須（RFC 9700 §2.1.1）

              
refresh_tokenaccess_token の更新refresh_token（+ 任意で縮小した scope）公開クライアントの refresh_token は送信者制約かローテーション必須（RFC 9700 §2.2.2）

              
client_credentialsバッチ・サーバー間（ユーザーなし）クライアント認証 + scope。refresh_token は通常返らない機密クライアントのみ

              
urn:ietf:params:oauth:grant-type:device_codeTV・CLI など入力が不自由な端末（RFC 8628）device_code をポーリング（interval 秒ごと）利用可。フィッシング（user_code の騙し取り）に注意

              
response_type=token（Implicit）かつての SPAaccess_token を URL フラグメントで直接受け取る使うべきでない（SHOULD NOT、RFC 9700 §2.1.2）

              
password（ROPC）かつての自社アプリユーザーのパスワードを Client が受け取って送る使ってはならない（MUST NOT、RFC 9700 §2.4）

    -d code_verifier="$verifier" | tee token.json | jq .

# id_token の payload を読む（base64url → base64 に直してパディング補完）
$ b64url_d() { local s; s=$(printf '%s' "$1" | tr '_-' '/+'); while (( ${#s} % 4 )); do s+='='; done; printf '%s' "$s" | base64 -d; }
$ b64url_d "$(jq -r .id_token token.json | cut -d. -f2)" | jq .

# access_token で API、期限切れなら refresh
$ curl -i https://api.example/v1/me -H "Authorization: Bearer $(jq -r .access_token token.json)"
$ curl -s https://idp.example/token -u 's6BhdRkqt3:gX1fBat3bV' \
    -d grant_type=refresh_token -d refresh_token="$(jq -r .refresh_token token.json)" | jq .

        
ローカルに IdP を立てる（Keycloak）

        
Keycloak 26 系をコンテナで起動すると、実物の Discovery 文書・JWKS・トークンエンドポイントを手元で観察できます（開発モード。管理者の環境変数名は 26 系のもの）。

        
$ docker run --rm -p 8080:8080 \
    -e KC_BOOTSTRAP_ADMIN_USERNAME=admin -e KC_BOOTSTRAP_ADMIN_PASSWORD=admin \
    quay.io/keycloak/keycloak:26.0.0 start-dev
$ curl -s http://localhost:8080/realms/master/.well-known/openid-configuration | jq .token_endpoint
"http://localhost:8080/realms/master/protocol/openid-connect/token"

      


      
      

        
ハマりどころ

        

          
    
            
  • Client で access_token を検証・解釈しない：access_token は API 向け。形式は AS の都合で変わります（opaque ↔ JWT）。Client がユーザー情報を知りたいなら id_token か userinfo_endpoint を使います。
    • 
            
  • id_token を API の認可に使わない：aud は Client の client_id で、API 宛てではありません。API には access_token を送ります。
    • 
            
  • トークンの保管場所：ブラウザの localStorage に置いたトークンは XSS で盗まれます。サーバーを持つ Web アプリはトークンをサーバー側に置き、ブラウザには HttpOnly; Secure; SameSite のセッション Cookie だけを渡す（BFF パターン）のが堅実です。
    • 
            
  • state をセッションに紐付けていない：固定値や、Cookie に紐付かない保存場所（全ユーザー共通のキャッシュ等）では CSRF を防げません。1 回使ったら消します。
    • 
            
  • redirect_uri の表記ゆれ：末尾 /、大文字小文字、http/https、ポート、クエリの有無で不一致になります。登録値をコピーして使います。
    • 
            
  • code の再利用：認可コードは 1 回限り。二重送信（リロード・リトライ）で invalid_grant になり、AS によってはそのコードで発行済みのトークンも失効させます（RFC 6749 §4.1.2）。
    • 
            
  • 時計のずれ：exp/iat の検証でサーバーの時刻がずれていると失敗します。NTP を確認し、許容スキューは数十秒程度に留めます。
    • 
            
  • JWKS のキャッシュと鍵ローテーション：未知の kid が来たら JWKS を再取得します。ただし毎回取得すると AS に負荷がかかるのでレート制限付きで。
    • 
            
  • Basic 認証のエンコード：RFC 6749 §2.3.1 では client_id・client_secret を application/x-www-form-urlencoded でエンコードしてから Base64 します。記号を含むシークレットで invalid_client になる典型原因です。
    • 
            
  • SPA から /token を直接呼ぶ：ブラウザからの POST /token はクロスオリジンなので、AS 側の CORS 許可が必要です（CORS のページ）。SPA は公開クライアントなので client_secret を埋め込まず、PKCE を使います。
    •
