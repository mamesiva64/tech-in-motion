CA と証明書チェーンどこで署名され、どこで検証されるか

サーバーの秘密鍵はサーバーの中で生まれて一度も外に出ません。CA に渡るのは CSR だけで、CA は自分の HSM の中にある中間 CA の鍵で TBSCertificate に署名します。クライアントは受け取った「リーフ + 中間」を、手元のトラストストアにあるルートまでつないで、各段の署名を発行者の公開鍵で検証します。このページではその全行程を、実際に作ったミニ CA（OpenSSL 3.5）と ACME の実メッセージで追いかけます。

秘密鍵のある場所サーバー：privkey.pem／CA：HSM 内の中間 CA 鍵
署名する場所CA の HSM（中間 CA「E1」の鍵で TBS に署名）
検証する場所クライアント（/etc/ssl/certs/ca-certificates.crt 等のルートまで）
仕様RFC 5280 / 2986 / 8555 / 6960 / 6962、CA/B Forum BR

サーバー運用者側：秘密鍵と CSR

CSR（Certificate Signing Request, PKCS #10 / RFC 2986）は「この公開鍵にこの名前で証明書をください」という申請書です。中身は 公開鍵 + subject + 要求する拡張で、それを申請者自身の秘密鍵で署名してあります。この署名は「申請者がこの公開鍵に対応する秘密鍵を本当に持っている」ことの証明（proof of possession）で、CA は発行前に必ず検証します。

チェーンとクライアント側の検証

サーバーは TLS の Certificate メッセージで リーフ + 中間を送ります（ルートは送らない、送っても信頼の根拠にはならない）。クライアントは issuer/subject と AKI/SKI で上へたどり、各証明書の署名を1 つ上の証明書に入っている公開鍵で検証し、最後に自分のトラストストアにあるルートに到達したら「信頼できる」と判断します（RFC 5280 §6）。

OCSP の Issuer Key Hash（9221CB1D…）は中間 CA の公開鍵の SHA-1 で、ここでは中間 CA 証明書の SKI と同じ値です（SKI を RFC 5280 §4.2.1.2 の方法 (1)＝公開鍵の SHA-1 で作っているため。OpenSSL の subjectKeyIdentifier = hash）。CRL / OCSP 応答はどちらも中間 CA E1 の鍵で署名されており、クライアントは証明書と同じくその署名を検証します。

subjectKeyIdentifier   = hash

[ v3_inter ]
basicConstraints       = critical, CA:TRUE, pathlen:0
keyUsage               = critical, digitalSignature, keyCertSign, cRLSign
extendedKeyUsage       = serverAuth, clientAuth
subjectKeyIdentifier   = hash
authorityKeyIdentifier = keyid:always

[ v3_leaf ]
basicConstraints       = critical, CA:FALSE

subjectKeyIdentifier   = hash

subjectAltName         = DNS:www.example.com, DNS:example.com

#--- ルート CA（自己署名。本物ならオフラインの HSM で行う）
openssl genpkey -algorithm EC -pkeyopt ec_paramgen_curve:P-384 -out root.key
openssl req -x509 -new -key root.key -sha384 -days 3650 \
  -subj "/C=JP/O=Example Trust/CN=Example Root CA R1" \
  -config pki.cnf -extensions v3_root -out root.crt

#--- 中間 CA（ルートが署名）
openssl genpkey -algorithm EC -pkeyopt ec_paramgen_curve:P-384 -out inter.key
openssl req -new -key inter.key -config pki.cnf \
  -subj "/C=JP/O=Example Trust/CN=Example Issuing CA E1" -out inter.csr
openssl x509 -req -in inter.csr -CA root.crt -CAkey root.key -sha384 -days 1825 \
  -extfile pki.cnf -extensions v3_inter -out inter.crt

#--- サーバー側：鍵と CSR（鍵はここから出さない）
openssl genpkey -algorithm EC -pkeyopt ec_paramgen_curve:P-256 -out server.key
chmod 600 server.key
openssl req -new -key server.key -subj "/CN=www.example.com" \
  -addext "subjectAltName=DNS:www.example.com,DNS:example.com" -out server.csr
openssl req -in server.csr -noout -verify      # Certificate request self-signature verify OK

#--- CA 側：中間 CA の鍵でリーフに署名
openssl x509 -req -in server.csr -CA inter.crt -CAkey inter.key -sha384 -days 90 \
  -extfile pki.cnf -extensions v3_leaf -out server.crt
cat server.crt inter.crt > fullchain.pem        # サーバーが送るのはこれ
openssl verify -show_chain -CAfile root.crt -untrusted inter.crt server.crt   # OK
openssl verify -CAfile root.crt -untrusted inter.crt -verify_hostname www.example.com server.crt
openssl verify -CAfile root.crt server.crt                  # error 20: 中間がない
cat inter.crt root.crt > bundle.pem
openssl verify -untrusted bundle.pem server.crt             # error 19: ルートを信頼していない
openssl verify -CAfile inter.crt server.crt                 # error 2: 中間をアンカーにしても上が無い

#--- TLS で試す（ターミナルを 2 つ使う）
# (A) 中間を送らないサーバー
openssl s_server -accept 8443 -cert server.crt -key server.key -www
# (B) クライアント → verify error:num=20 / Verify return code: 21
openssl s_client -connect 127.0.0.1:8443 -servername www.example.com \

# (A') 中間も送るサーバー（nginx の fullchain.pem に相当）
openssl s_server -accept 8443 -cert server.crt -cert_chain inter.crt -key server.key -www

ハマりどころ

中間証明書の送り忘れ：ssl_certificate に cert.pem を指定するとリーフだけが送られます。ブラウザは AIA の CA Issuers URL から中間証明書を取りに行ったり、以前に見た・事前配布された中間証明書で補完したりして表示できてしまうことがあるため気付きにくく、curl・Java・Python などで unable to get local issuer certificate になります。確認は openssl s_client -showcerts で「何枚送られてくるか」を見ます。
チェーンの順序：先頭は必ずリーフ、その後に中間を「下から上」の順に並べます（cat server.crt inter.crt）。TLS 1.2（RFC 5246）は厳密な順序を要求し、TLS 1.3（RFC 8446 §4.4.2）は先頭以外の順序を緩めましたが、nginx は ssl_certificate の最初の 1 枚をサーバー証明書として秘密鍵と突き合わせるので、順序を逆にすると起動時に key values mismatch で失敗します。
ルートは送らなくてよい：信頼の根拠はクライアント側のストアにあるルートだけです。サーバーがルートを送っても信頼は増えず、バイト数が増えるだけです（送っても害はほぼありません）。
-CAfile と -untrusted の違い：-CAfile に入れた証明書は「信頼の起点（トラストアンカー）」、-untrusted は「パス構築に使ってよいが信頼はしない中間」です。中間 CA を -CAfile に入れてもルートまで届かなければ error 2（-partial_chain を付けると中間をアンカーとして扱う）。
秘密鍵のパーミッション：privkey.pem は 0600（certbot 0.29.0 以降の既定）で root 所有。nginx はマスタープロセス（root）が起動時に読み込むのでワーカーの権限は不要です。鍵をリポジトリやチケットに貼ったら、失効と鍵の作り直しが必要です。
ワイルドカードの範囲：*.example.com は www.example.com や api.example.com に一致しますが、example.com 自身や a.b.example.com（2 階層下）には一致しません。Let's Encrypt でワイルドカードを取るには DNS-01 が必要です。
時計のずれ：クライアントの時刻が notBefore より前だと error 9 … certificate is not yet valid、notAfter より後だと error 10 … certificate has expired。発行直後の証明書が一部の端末だけで失敗する場合は端末の時刻を疑います。
有効期間の短縮：公開 TLS 証明書の最大有効期間は 2026-03-15 から 200 日、2027-03-15 から 100 日、2029-03-15 から 47 日（CA/B Forum SC-081v3）。手動更新の運用は成り立たなくなるので ACME での自動更新（certbot renew の timer）を前提にします。
Git Bash の -subj：Windows の Git Bash では "/CN=www.example.com" が Windows パスに変換されて req が失敗します。MSYS_NO_PATHCONV=1 を付けるか、"//CN=www.example.com" と書きます。
