Container · Docker Engine / OCI

DockerDockerfile → イメージ（レイヤー）→ コンテナ。その実体を /var/lib/docker と /proc で確かめる

docker run は魔法ではありません。CLI が UNIX ソケット越しに REST API を叩き、dockerd → containerd → runc が namespaces と cgroup を設定して execve するだけです。イメージは sha256 で名前の付いた JSON と tar の集まり、コンテナのファイルシステムは overlay マウント、-p 8080:3000 は iptables の DNAT ルール。このページではそれぞれを実際のファイル・コマンド出力で分解します。

実行チェーンdockerd → containerd → containerd-shim-runc-v2 → runc
実体の置き場/var/lib/docker/overlay2/・/proc/<pid>/ns/・/sys/fs/cgroup/…/docker-<id>.scope/
仕様OCI Image Spec v1.1 / Runtime Spec v1.2・Docker Engine API

全体像：docker run は何を起動しているのか

docker コマンド自体はコンテナを作りません。やっていることは HTTP リクエストの送信だけです。受け取った dockerd がイメージ・ネットワーク・ストレージを準備し、OCI Runtime Spec の config.json を作って containerd に渡し、最終的に runc がカーネルの機能（clone(2) の namespace フラグ、cgroup ファイルへの書き込み、pivot_root(2)）を使ってプロセスを起動します。

本ページの出力例は Ubuntu 24.04 + Docker Engine 28.5（API v1.51）+ overlay2 ストレージドライバ + cgroup v2（systemd cgroup driver）を前提にしています。Engine 29 以降の新規インストールでは containerd image store が既定になり、レイヤーの置き場所が変わります（後述）。コンテナ ID・PID・digest はこのページ用の例示値です。

Docker Engine 25 以降の docker save は OCI Image Layout（oci-layout + index.json + blobs/sha256/）で出力し、旧来のツール向けに manifest.json と repositories も同梱します。レイヤー blob は非圧縮 tar（application/vnd.oci.image.layer.v1.tar）なので、ファイル名の digest は config の diff_ids と一致します。レジストリに push すると gzip 圧縮されるため、manifest の layers[].digest は別の値になります。

Engine 29 以降の新規インストール（containerd image store）では場所が違います。レイヤーは containerd の snapshotter（overlayfs）が管理し、docker info -f '{{ .DriverStatus }}' が [[driver-type io.containerd.snapshotter.v1]] を返します。/var/lib/docker/overlay2 は使われず、docker inspect の GraphDriver.Data も上の例のようには埋まりません。実際のマウントは findmnt -t overlay で確認できます（lowerdir / upperdir / workdir の仕組み自体は同じです）。従来の overlay2 に戻すには /etc/docker/daemon.json に "features": {"containerd-snapshotter": false} を書きます。

  • PREROUTING：ホスト自身の IP 宛て（--dst-type LOCAL）のパケットを DOCKER チェーンへ。ここで宛先が 172.17.0.2:3000 に書き換わり、以降は FORWARD 経路で docker0 に流れます。
  • OUTPUT：ホスト上のプロセスからの通信も対象。ただし 127.0.0.0/8 宛ては除外されるので、curl localhost:8080 は docker-proxy が受けて中継します。
  • POSTROUTING：コンテナから外への通信を MASQUERADE（送信元をホストの IP に）。net.ipv4.ip_forward=1 も Docker が有効にします。
  • Docker 28 以降は filter テーブルに DOCKER-USER、DOCKER-FORWARD、DOCKER-BRIDGE、DOCKER-CT などのチェーンも作られます。独自の制限は DOCKER-USER に書きます。

サービス名で名前解決できるのはユーザー定義ネットワーク（docker network create、Compose の既定）だけで、そこではコンテナの /etc/resolv.conf が組み込み DNS 127.0.0.11 を指します。詳しくは Docker Compose と DNS のページへ。

ハマりどころ

latest は「最新」ではありません。タグを省略したときに補われるだけの普通のタグ名で、いつ誰が付け替えたかは分かりません。本番では node:22-alpine@sha256:… のように digest で固定するか、少なくともバージョンタグを使います。同じタグでも pull した時期で中身（digest）が変わります。
秘密情報は後から消してもレイヤーに残ります。COPY .env . の後に RUN rm .env しても、COPY の層の tar には入ったままで、docker save して展開すれば誰でも読めます。ENV / ARG の値も config や docker history に残ります。ビルド時の秘密は RUN --mount=type=secret,id=npmrc,target=/root/.npmrc npm ci ＋ docker build --secret id=npmrc,src=$HOME/.npmrc . で渡します（どの層にも書かれません）。
exec 形式と shell 形式。CMD node server.js（shell 形式）は ["/bin/sh", "-c", "node server.js"] として保存され、シェルが間に入ります（シェルの実装によっては単一コマンドを exec で置き換えることもあり、挙動が環境依存）。CMD ["node", "server.js"]（exec 形式）ならアプリが直接 PID 1 になります。起動スクリプトの最後は exec "$@" / exec node server.js。確実にしたいなら docker run --init。
Docker Desktop は VM の中で動いています。macOS / Windows の Docker Desktop では dockerd・/var/lib/docker・/proc/<pid>・iptables は Linux VM（Windows は WSL 2）の中にあり、ホスト OS からは見えません。-v のホストパスは VM へのファイル共有を経由するので遅く、パーミッションの見え方も Linux と異なります。コンテナからホストへは host.docker.internal を使います。
-p は ufw / firewalld を素通りします。DNAT は nat テーブルの PREROUTING で行われ、パケットは INPUT ではなく FORWARD を通るため、ufw の INPUT ルールでは止まりません。外に出したくないポートは -p 127.0.0.1:8080:3000 のようにバインド先を限定するか、DOCKER-USER チェーンで制限します。
/var/run/docker.sock へのアクセスは root 権限と同じです。docker グループに入れる、ソケットをコンテナに -v /var/run/docker.sock:/var/run/docker.sock でマウントする、TCP で無認証公開する——いずれも docker run -v /:/host --privileged … でホストを乗っ取れることを意味します。
書き込みは docker rm で消えます。コンテナ内の変更は upperdir（overlay2/<id>/diff）にあり、コンテナ削除と同時に消えます。DB などのデータは -v 名前:/path（/var/lib/docker/volumes/名前/_data）か bind mount に置きます。copy_up はファイル丸ごとのコピーなので、巨大ファイルを少しだけ書き換える処理も遅くなります。
ディスクが静かに埋まります。json-file ログ（log-opts 未設定だと無制限）、dangling イメージ、ビルドキャッシュ、停止コンテナの upperdir。docker system df で内訳を見て、docker system prune / docker builder prune で掃除します。
Engine 29 以降の新規インストールはパスが違います。containerd image store が既定になり、/var/lib/docker/overlay2 や GraphDriver.Data を前提にしたスクリプトは動きません。docker info -f '{{ .DriverStatus }}' で確認してください。
