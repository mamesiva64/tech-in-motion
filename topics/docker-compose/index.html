docker compose up -d で作られるもの

Compose は「コンテナを起動する魔法」ではなく、Docker Engine API のクライアントです。compose.yaml を読み、変数を展開し、プロジェクト名を決め、その名前を接頭辞にしてネットワーク → ボリューム → コンテナの順に作成 API を呼びます。作ったものには必ずラベルを貼り、次回以降は 状態ファイルではなくラベルで自分のリソースを探します。

プロジェクト名は -p ＞ COMPOSE_PROJECT_NAME ＞ トップレベル name: ＞ compose.yaml のあるディレクトリ名 の順で決まります。使える文字は英小文字・数字・-・_ で、先頭は英小文字か数字です。プロジェクト名が変わると、ネットワークもボリュームも別物として新しく作られます。

const http = require('node:http');
const net = require('node:net');

const { hostname, port } = new URL(process.env.DATABASE_URL);
const dbPort = Number(port) || 5432;

// DB に TCP 接続できるかだけを確かめる（デモ用。実アプリでは pg などのドライバを使う）
function checkDb() {
  return new Promise((resolve, reject) => {
    const sock = net.connect({ host: hostname, port: dbPort }, () => { sock.end(); resolve(); });
    sock.setTimeout(2000, () => sock.destroy(Object.assign(new Error('timeout'), { code: 'ETIMEDOUT' })));
    sock.on('error', reject);
  });
}

process.on('SIGTERM', () => process.exit(0));   // PID 1 は SIGTERM を自分で処理する必要がある

checkDb()
  .then(() => {
    console.log(`db reachable at ${hostname}:${dbPort}`);
    const listenPort = Number(process.env.PORT) || 3000;
    http.createServer(async (req, res) => {
      res.setHeader('Content-Type', 'application/json');
      try {
        await checkDb();
        res.end(JSON.stringify({ status: 'ok', db: 'up', env: process.env.NODE_ENV }));
      } catch (e) {
        res.statusCode = 503;
        res.end(JSON.stringify({ status: 'error', db: e.code }));
      }
    }).listen(listenPort, () => console.log(`api listening on :${listenPort}`));
  })
  .catch((e) => {
    console.error(`db connect failed (${e.code}) ${hostname}:${dbPort}`);
    process.exit(1);
  });

compose.yaml の主要キー

キー書き方の例実際に起きること
servicesservices: { web: …, api: …, db: … }サービスごとにコンテナ <project>-<service>-1 を作る。サービス名はそのままネットワーク上の DNS 名になる
imageimage: postgres:16-alpineローカルに無ければ pull。build と併用するとビルド結果にこの名前が付く
buildbuild: ./api / build: { context: ./api, target: dev }コンテキストをビルドし、image 未指定なら myapp-api と命名。up --build で毎回再ビルド
ports"8080:80", "127.0.0.1:5432:5432"ホスト側のポートを公開（DNAT）。ホスト IP を省略すると 0.0.0.0（と [::]）。サービス間通信には不要
expose- "3000"ホストには公開しない。同じネットワークのコンテナからは expose が無くても届く（宣言的な意味合い）
environmentNODE_ENV: productionコンテナの環境変数。値の中の ${VAR} は Compose が先に展開する
env_file- ./api/api.envファイルの KEY=VALUE をコンテナの環境変数にする。environment の方が優先。compose.yaml の展開には使われない
volumes（サービス内）dbdata:/var/lib/postgresql/data, ./web/nginx.conf:/etc/…:ro左辺が名前なら名前付きボリューム、./ や / で始まればバインドマウント。:ro で読み取り専用
volumes（トップレベル）volumes: { dbdata: {} }myapp_dbdata を作成。external: true なら作らず既存を使う（down -v でも消えない）
networksnetworks: [backend]省略時は全サービスが myapp_default に参加。分けると別ネットワークのサービスは名前解決も通信もできない
depends_ondb: { condition: service_healthy }起動（と停止）の順序。service_started / service_healthy / service_completed_successfully。短縮形は service_started
healthchecktest: ["CMD-SHELL", "pg_isready …"]Engine がコンテナ内で定期実行し、終了コード 0 なら healthy。interval / timeout / retries / start_period
restartno / always / on-failure[:N] / unless-stoppedEngine の再起動ポリシー。落ちたコンテナを dockerd が再起動する（Compose は常駐しない）
profilesprofiles: [debug]そのプロファイルが有効（--profile debug / COMPOSE_PROFILES）なときだけ起動するサービスにする
deploy.resourceslimits: { memory: 256M, cpus: "0.5" }cgroup の上限としてコンテナに設定される（docker inspect の HostConfig.Memory など）

起動順序：depends_on と healthcheck

depends_on の短縮形（- db）は「db コンテナが running になったら次へ」という意味で、PostgreSQL が接続を受け付けられる状態かどうかは見ていません。condition: service_healthy を付けると、Compose は依存先コンテナの State.Health.Status を 500 ms 間隔で確認し、healthy になってから依存元を起動します。

condition依存元を起動するタイミング向いている依存先
service_started依存先コンテナが running になった時点（短縮形 - db と同じ）起動直後から使える／自前でリトライするもの
service_healthy依存先の healthcheck が healthy になった時点。unhealthy や終了なら up 自体がエラーDB・メッセージブローカーなど初期化に時間がかかるもの
service_completed_successfully依存先が終了コード 0 で終わった時点マイグレーション・初期データ投入などの一回きりのジョブ
healthcheck のキー意味この例の値
testコンテナ内で実行するコマンド。CMD は exec 形式、CMD-SHELL は /bin/sh -c 経由。終了コード 0 = 成功、それ以外 = 失敗（pg_isready の「応答なし」は 2）pg_isready -h 127.0.0.1 …
intervalチェックの間隔5s
timeout1 回のチェックの制限時間。超えたら失敗扱い3s
retries連続でこの回数失敗したら unhealthy5
start_period起動直後の猶予。この間の失敗は retries に数えない（成功すれば即 healthy）10s
なぜ -h 127.0.0.1 を付けるのか：公式 postgres イメージは初回起動時、initdb の後にUnix ソケットだけで待ち受ける一時サーバーを立ててユーザーや DB を作り、いったん停止してから本番のサーバーを起動します。pg_isready を -h なし（Unix ソケット）で実行すると、この一時サーバーに対して accepting connections を返してしまうことがあります。TCP で確認すれば、他のコンテナから実際に接続できる状態になってから healthy になります。なお pg_isready は認証を行わないので、ユーザー名が違っても「受け付け中」かどうかは判定できます。

失敗ケース：localhost の罠と起動競合

Compose でいちばん多い事故は「ホストでは localhost:5432 で繋がったのに、api コンテナからは繋がらない」です。各コンテナは別々の network namespace を持ち、lo（127.0.0.1）もコンテナごとに別物です。api コンテナの localhost は api コンテナ自身を指し、そこでは誰も 5432 番を待ち受けていません。

手元で試す

Docker Engine と Compose プラグインが入った Linux（または Docker Desktop）で、空のディレクトリにコピペすれば再現できます。/var/lib/docker を直接見る手順は Linux ホスト専用です。

mkdir -p myapp/api/src myapp/web/public && cd myapp

cat > .env <<'EOF'
POSTGRES_PASSWORD=devpass
APP_PORT=8080
EOF

printf 'LOG_LEVEL=info\nPORT=3000\n' > api/api.env
printf '<h1>myapp</h1>\n' > web/public/index.html

cat > api/Dockerfile <<'EOF'
FROM node:22-slim
WORKDIR /app
COPY src ./src
EXPOSE 3000
CMD ["node", "src/server.js"]
EOF

cat > web/nginx.conf <<'EOF'
server {
    listen 80;
    server_tokens off;
    location /api/ { proxy_pass http://api:3000/; }
    location / { root /usr/share/nginx/html; index index.html; }
}
EOF

# compose.yaml / compose.override.yaml / api/src/server.js は
# 上の「compose.yaml と周辺ファイルの実物」の内容をそのまま保存する
docker compose config                     # 最終形（.env と override が反映済み）
docker compose up -d --wait               # db が healthy、他が running になるまで待つ
docker compose ps
curl -s http://localhost:8080/api/health  # {"status":"ok","db":"up","env":"development"}

docker network ls --filter label=com.docker.compose.project=myapp
docker volume inspect myapp_dbdata --format '{{ .Mountpoint }}'
docker inspect myapp-db-1 --format '{{json .Config.Labels}}'

docker compose exec api cat /etc/resolv.conf   # nameserver 127.0.0.11
docker compose exec api getent hosts db        # 172.18.0.x      db
docker compose exec db pg_isready -h localhost     # localhost:5432 - accepting connections（db の中では OK）

# api の接続先を localhost にしてみる
sed -i 's/@db:5432/@localhost:5432/' compose.yaml
docker compose up -d api
docker compose logs api                            # db connect failed (ECONNREFUSED) localhost:5432
sed -i 's/@localhost:5432/@db:5432/' compose.yaml && docker compose up -d api   # 元に戻す

# データの寿命
docker compose exec db psql -U app -c "CREATE TABLE orders(id int); INSERT INTO orders VALUES (1),(2),(3);"
docker compose down && docker compose up -d --wait
docker compose exec db psql -U app -tAc "SELECT count(*) FROM orders"   # 3（残っている）
docker compose down -v && docker compose up -d --wait
docker compose exec db psql -U app -tAc "SELECT count(*) FROM orders"   # ERROR:  relation "orders" does not exist

ハマりどころ

  • コンテナ内の localhost はそのコンテナ自身。他サービスへは db:5432 のようにサービス名＋コンテナ側ポートで接続します（ports の左側の番号ではありません）。
  • depends_on: [db] は「起動した」しか待ちません。DB の準備完了を待つには condition: service_healthy と healthcheck。それでもアプリ側の再接続処理はあった方が安全です（DB の再起動時などに備えて）。
  • .env はコンテナに渡りません。compose.yaml の ${...} 展開用です。渡したい値は environment で参照するか env_file を使います。また .env はプロジェクトディレクトリ（通常 compose.yaml の場所）から読まれます。
  • $ は Compose が先に展開します。コンテナ内のシェルに展開させたい $VAR は $$VAR と書きます（healthcheck の $${POSTGRES_USER} がその例）。パスワードに $ を含む場合も同様です。
  • down -v は DB のデータを消します。また -p やディレクトリ名が変わるとボリューム名も変わり（staging_dbdata など）、「データが消えた」ように見えます。守りたいボリュームは external: true にする手もあります。
  • ports: "5432:5432" はホストの全インターフェースで公開されます。開発用 DB は "127.0.0.1:5432:5432" に。Docker が追加する iptables ルールは ufw などホスト側のファイアウォール設定より先に評価されることがあります。
  • ポート指定は引用符で文字列に。YAML 1.1 のパーサでは xx:yy 形式の数値が 60 進数として解釈されることがあるためです（"8080:80"）。
  • nginx は起動時に proxy_pass のホスト名を解決して保持します。api を作り直して IP が変わると 502 になることがあります。resolver 127.0.0.11 valid=10s; と変数を使った proxy_pass で都度解決させるか、web を再起動します。
  • docker compose down が 10 秒かかるのは、PID 1 のプロセスが SIGTERM を処理していないからです。アプリで SIGTERM を処理するか、サービスに init: true を付けます。
  • -f を付けると compose.override.yaml は自動で読まれません。本番用に -f compose.yaml -f compose.prod.yaml とするのはこの性質を利用したものです。
  • restart / stop / start は設定変更を反映しません。compose.yaml や .env を変えたら docker compose up -d（変わったサービスだけ作り直されます）。
  • PostgreSQL 18 以降の公式イメージはデータの置き場所が変わりました。PGDATA が /var/lib/postgresql/18/docker になり、ボリュームは /var/lib/postgresql にマウントする前提です。このページの例（16）のパスをそのまま 18 に使わないでください。
  • Docker Desktop（macOS / Windows）では /var/lib/docker/volumes はホスト OS 上にありません。Linux VM の中にあるため、ls で見るならコンテナ経由（docker run --rm -v myapp_dbdata:/v alpine ls /v）が確実です。
