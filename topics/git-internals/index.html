Git の中身blob・tree・commit と .git ディレクトリを、実際のバイトとハッシュで

Git のリポジトリは「中身のハッシュ値を名前にしたファイルの集まり（オブジェクト DB）」と「そのハッシュ値を書いただけの小さなファイル（refs）」でできています。git add や git commit で .git/ のどこに・どんなバイト列が・どんな名前で書かれるかを、このページ上で SHA-1 を実際に計算しながら追います。

保存場所.git/objects/ce/013625…（ID の先頭 2 桁がディレクトリ）
オブジェクト IDSHA-1("blob 6\0hello\n") = ce013625…
ブランチの実体.git/refs/heads/main：40 桁 hex + 改行 = 41 バイト
仕様gitformat-index / gitrepository-layout / Pro Git 10 章

全体像：3 つの置き場所

ファイルは 3 か所を移動します。作業ツリー（普通のファイル）→ git add で index（.git/index、次のコミットの予定表）と オブジェクト DB（.git/objects/）→ git commit で tree と commit オブジェクトが作られ、ref（.git/refs/heads/main）が新しい commit を指すように書き換わります。

置き場所実体中身書き換えるコマンド
作業ツリー./hello.txt普通のファイルエディタ、git checkout / git switch / git restore
index（ステージ）.git/indexパス・モード・blob ID・stat 情報の一覧（バイナリ、先頭 DIRC）git add, git rm --cached, git update-index
オブジェクト DB.git/objects/xx/…、.git/objects/pack/blob / tree / commit / tag（zlib 圧縮、追記のみ）git add, git commit, git hash-object -w, git gc

HEAD が ref: refs/heads/main を指しているのに refs/heads/main ファイルが無い状態を「unborn branch」と呼びます。最初のコミットで初めてこのファイルが作られます。既定のブランチ名は init.defaultBranch の設定で決まり、未設定なら Git 2.x では master です（Git 3.0 で main に変わる予定と git init 自身がヒントを表示します）。

git add = blob を作る

git add hello.txt は、ファイルの中身に blob <バイト数>\0 というヘッダを付けて SHA-1 を計算し、その値を名前にして zlib 圧縮した中身を .git/objects/ に保存します。ファイル名は blob に入りません（名前は tree が持ちます）。同じ中身なら、どのリポジトリ・どのパスでも同じ ID になります。

改ざん検知：1 バイト変えると全部変わる

        
オブジェクトの ID は中身のハッシュで、tree は blob の ID を、commit は tree と parent の ID を中身に含みます。したがって過去の blob を 1 バイトでも変えると、その ID が変わり、それを含む tree・commit・子孫の commit の ID が連鎖してすべて変わります。ブランチや他人の clone が指している ID とは一致しなくなるので、黙って過去を書き換えることはできません。

git cat-file や git checkout は、ローカルの loose object を読むたびに SHA-1 を再計算しているわけではありません（上の例でも hellO がそのまま出ます）。検知するのは git fsck と、clone / fetch / push で受け取った側（index-pack が受信したオブジェクトの ID を計算し直す）です。エラーの文言は Git のバージョンやコードパスで異なり、hash mismatch for <path> (expected <id>) という形もあります。

        
「ID が変わる」ことで守れるのは既に ID を知っている相手に対してです。攻撃者が履歴を丸ごと作り直して新しい ID 一式を配った場合は、それが正しい履歴かは別の手段（署名付きタグ・署名付きコミット git verify-commit / git verify-tag、信頼できるリモートとの比較）で確かめます。なお Git 2.13 以降の SHA-1 は衝突攻撃を検知する SHA-1DC 実装です。

      


      
      

        
packfile：git gc 後の姿

        
loose object はオブジェクトごとに 1 ファイルなので、数が増えると git gc（または自動の git gc --auto、push / fetch の転送）で 1 つの .pack にまとめられます。似た blob は差分（delta）で保存され、.idx が ID → pack 内オフセットの索引になります。

SHA-256 リポジトリ

        
git init --object-format=sha256 で作ったリポジトリは、同じ形式（blob <size>\0…）を SHA-256 でハッシュし、ID が 64 桁になります。ID が SHA-1 リポジトリとは別物になるため、SHA-1 のリポジトリ（多くのホスティングサービス上のもの）とそのまま push / fetch し合うことはできません。Git 3.0 では新規リポジトリの既定を SHA-256 にする計画です（Documentation/BreakingChanges）。

        
$ git init -q --object-format=sha256 demo256 && cd demo256
$ cat .git/config
[extensions]
	objectformat = sha256
[core]
	repositoryformatversion = ⟪1⟫
	…
$ printf 'hello\n' | git hash-object --stdin
⟪2cf8d83d9ee29543b34a87727421fdecb7e3f3a183d337639025de576db9ebb4⟫
$ printf 'blob 6\0hello\n' | sha256sum
2cf8d83d9ee29543b34a87727421fdecb7e3f3a183d337639025de576db9ebb4  -

3 コミットでオブジェクトは 9 個（commit 3・tree 3・blob 3）。blob ce013625… と fc72a5c1… は複数の tree から共有されていて、ファイルとしては 1 回しか保存されていません。

      


      
      

        
コマンド早見表（plumbing）

        

          

            
コマンド主なフラグ何が起きるか

            
              
git hash-object file-w 書き込む, --stdin, -t tree|commitblob の ID を計算（-w で .git/objects に保存）

              
git cat-file -p <id>-t 種類, -s サイズ, -p 整形表示, --batch-all-objects --batch-checkオブジェクトを読む

              
git ls-tree <tree-ish>-r 再帰, -l サイズ付き, --name-onlytree のエントリ一覧

              
git ls-files --stage-s, --debugindex の中身（mode・blob ID・stage 番号・パス）

              
git update-index --add --cacheinfo100644,<id>,path作業ツリーを介さず index にエントリを追加

              
git write-treeindex から tree オブジェクトを作り ID を出力

              
git mktree--missingls-tree 形式のテキストから tree を作る

              
git commit-tree <tree>-p <parent>, -m msgcommit オブジェクトを作り ID を出力（ref は動かさない）

              
git update-ref refs/heads/main <id>-d 削除, 第 3 引数で旧値確認ref を書き換える（reflog も記録）

              
git symbolic-ref HEADHEAD refs/heads/x で変更HEAD が指すブランチを読む / 書く

              
git rev-parse <rev>HEAD~1, main^{tree}, --show-object-format名前を ID に解決

              
git show-ref--heads, --tagsrefs と ID の一覧（packed-refs も含む）

              
git count-objects -vloose / pack のオブジェクト数とサイズ

              
git fsck--full, --unreachable, --lost-found全オブジェクトのハッシュと接続を検査

              
git verify-pack -vpack 内のオブジェクト・delta を一覧

              
git gc--aggressive, --prune=nowloose object を pack にまとめ、不要なものを削除

            
          

        

        
porcelain → plumbing 対応表

        

          

            
いつものコマンド相当する plumbing 操作

            
              
git add hello.txtgit hash-object -w hello.txt + git update-index --add hello.txt

              
git commit -m msggit write-tree → git commit-tree <tree> -p HEAD -m msg → git update-ref HEAD <commit>

              
git branch featuregit update-ref refs/heads/feature HEAD

              
git switch feature作業ツリーと index を feature の tree に合わせ、git symbolic-ref HEAD refs/heads/feature

              
git switch --detach <id>同上で、.git/HEAD に ID を直接書く

              
git tag -a v1.0 -m msgtag オブジェクトを書く（git mktag 相当）→ git update-ref refs/tags/v1.0 <tag>

              
git logHEAD から parent を辿って git cat-file commit を繰り返す（git rev-list HEAD）

ハマりどころ

        
sha1sum hello.txt は git の ID と一致しない。git はヘッダ blob <size>\0 を付けてからハッシュします。

        
改行コードの自動変換で ID が変わる。Windows の core.autocrlf=true では、作業ツリーの CRLF が LF に変換されてから blob になります。「同じファイルなのに ID が違う」ときは git ls-files --eol と .gitattributes を確認します。

        
空のディレクトリはコミットできない。tree のエントリは blob か tree で、空の tree を指すエントリは git add では作られません。慣習として .gitkeep を置きます。

        
tree 内の mode は 40000。生のオブジェクトではディレクトリの mode は先頭 0 なしの 40000 ですが、git ls-tree は 040000 と 6 桁で表示します。自前でパースするときの落とし穴です。

        
ブランチを消してもコミットはすぐには消えない。refs から辿れなくなった commit も reflog（既定 90 日、到達不能なものは 30 日）と gc.pruneExpire（既定 2 週間）の間は残ります。git reflog で ID を探して git branch rescue <id> で戻せます。

        
detached HEAD でのコミット。.git/HEAD に ID が直接書かれた状態でコミットすると、どのブランチも指さない commit ができます。別のブランチに switch すると辿れなくなるので、残すなら先に git switch -c <name>。

        
.git/refs/heads/ を直接 cat しても無いことがある。git gc 後は .git/packed-refs に、reftable 形式なら .git/reftable/ に入っています。スクリプトでは git rev-parse を使います。
