HTTPTCP の上を流れる「テキストの行」と、それを返すのは誰か

HTTP/1.1 のメッセージは、GET /index.html HTTP/1.1 で始まり \r\n で区切られた行の並びにすぎません。このページでは curl -v の > < 行、ワイヤ上の 16 進ダンプ、nginx とアプリのどちらが 502 や 415 を返したのか、ETag から 304 が生まれる瞬間、HTTP/2 の 9 バイトのフレームヘッダまでを、実物のまま順に再生します。

何をリクエストライン + ヘッダ + 空行 \r\n + ボディ
どうやって見るcurl -v / curl --trace-ascii - / -w '%{http_code}'
仕様RFC 9110（意味論）/ 9111（キャッシュ）/ 9112（HTTP/1.1）/ 9113（HTTP/2）/ 9114（HTTP/3）

全体像：curl -v の 1 往復を分解する

HTTP/1.1 では、TCP 接続（HTTPS なら TLS の中）にテキストの行をそのまま書き込みます。改行は必ず CR LF（0d 0a）で、空行（\r\n だけの行）がヘッダの終わりです。ボディの長さは Content-Length か Transfer-Encoding: chunked で決まります。

メッセージの構造（RFC 9112）

RFC 9112 §2.1 の ABNF がすべてです。リクエストとレスポンスは開始行（start-line）だけが違います。

HTTP-message   = start-line CRLF
                 *( field-line CRLF )
                 CRLF
                 [ message-body ]
start-line     = request-line / status-line
request-line   = method SP request-target SP HTTP-version
status-line    = HTTP-version SP status-code SP [ reason-phrase ]
部品リクエストでの実物レスポンスでの実物メモ
start-lineGET /index.html HTTP/1.1HTTP/1.1 200 OK区切りは SP 1 個。reason-phrase は無視してよい（412 PRECONDITION FAILED のように大文字で返すサーバーもある）
field-lineHost: www.example.comContent-Type: text/html名前は大文字小文字を区別しない。: の前に空白は不可
空行\r\n（0d 0a）だけの行これがないとサーバーはヘッダの続きを待ち続ける
message-bodyPOST/PUT/PATCH の JSON などHTML・JSON・画像など長さは Content-Length か Transfer-Encoding: chunked。HEAD への応答と 204 / 304 はボディなし

メソッドと冪等性（safe / idempotent）

RFC 9110 §9.2.2 の定義では、idempotent（冪等）とは「同じリクエストを何回送っても、サーバー上の意図した効果が 1 回のときと同じ」ことです。レスポンスが同じである必要はありません（2 回目の DELETE が 404 でも冪等）。冪等なメソッドは、接続が切れたときにクライアントやプロキシが自動で再送できます。

キャッシュと条件付きリクエスト（RFC 9111 / RFC 9110 §13）

Cache-Control も Expires もなく Last-Modified だけがある場合、キャッシュは経過時間の一部（RFC 9111 §4.2.2 は「典型的には 10%」と記述）を鮮度として推測してよいことになっています。意図しないキャッシュを避けるには、必ず Cache-Control を明示します。

# 303 ->   "method": "GET",
# 307 ->   "method": "POST",
# 308 ->   "method": "POST",
$ docker run --rm -d -p 8080:80 --name web nginx:1.27
$ curl -sI http://localhost:8080/ | grep -iE '^(etag|last-modified|content-length)'
$ etag=$(curl -sI http://localhost:8080/ | tr -d '\r' | awk 'tolower($1)=="etag:"{print $2}')

$ curl -s -o /dev/null -w '%{http_code}\n' -H 'If-None-Match: "nope"' http://localhost:8080/

ハマりどころ

curl -d で JSON を送ると form 扱い：-d は Content-Type: application/x-www-form-urlencoded を付けます。JSON なら --json か -H 'Content-Type: application/json'。サーバーが 415 を返すか、req.body が空になります。
-X POST と -L の組み合わせ：-X はリダイレクト後のリクエストにも適用されるので、301 の先にも POST を送ります（curl は Note: Unnecessary use of -X or --request, POST is already inferred. と警告します）。-d を付けていれば -X POST は不要です。
API の http→https に 301 を使う：POST が GET に変わってボディが消え、アプリには「GET /v1/users」だけが届きます。メソッドを保つ 308 を使うか、そもそも http を受けないようにします。
改行が LF だけ：手書きのリクエストで \n しか送らないと、サーバーによって 400 になるか、ヘッダ終端を認識できずに待ち続けます。printf で \r\n を明示します。
502 と 504 をアプリのログで探す：nginx が作った 502/504 はアプリのログに出ないことがあります。まず /var/log/nginx/error.log の connect() failed / upstream timed out を見ます。504 の後もアプリ側のクエリは走り続けている点にも注意します。
no-cache は「キャッシュしない」ではない：保存したうえで毎回再検証する指示です。保存させたくないなら no-store。
Cache-Control を付けずに配信：Last-Modified だけだとブラウザがヒューリスティックに鮮度を決め、デプロイ直後に古い JS/CSS が使われ続けることがあります。
ヘッダ名の大文字小文字：HTTP/1.1 では区別しませんが、HTTP/2・HTTP/3 では小文字で送る規則です（content-type）。HTTP/2 で受けると curl -v の < 行はすべて小文字になり、HTTP/1.1 でも小文字で返すサーバーがあります。ヘッダ名を文字列比較するコードは小文字に揃えてから比較します。
