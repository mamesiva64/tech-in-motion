SSH鍵交換・ホスト鍵確認・公開鍵認証を、実際のファイルとメッセージで

ssh alice@server.example.com の 1 行の裏で、クライアントとサーバーは「暗号路を作る（鍵交換）」「相手が本物のサーバーか確かめる（ホスト鍵）」「ユーザーが鍵の持ち主か確かめる（公開鍵認証）」の 3 段階を踏みます。このページでは、それぞれでどのファイルが読まれ、どのバイト列に誰が署名し、どこで検証されるかを OpenSSH 10.3 の実際の出力で追います。

クライアントの鍵~/.ssh/id_ed25519（600）と id_ed25519.pub
サーバーが照合~/.ssh/authorized_keys・/etc/ssh/ssh_host_ed25519_key
ホストの確認~/.ssh/known_hosts の公開鍵で交換ハッシュ H の署名を検証
仕様RFC 4251–4254 / RFC 8709 / RFC 8731

全体像：どのファイルがどこで使われるか

SSH の鍵は 2 種類あります。ユーザー鍵（クライアントの ~/.ssh/id_ed25519）は「このユーザーは本人か」を、ホスト鍵（サーバーの /etc/ssh/ssh_host_ed25519_key）は「このサーバーは本物か」を証明します。どちらも公開鍵だけを相手側に登録し（authorized_keys / known_hosts）、秘密鍵は持ち主のマシンから出ません。

段階仕様どこで使うファイル何が起きるか
トランスポート層RFC 4253ssh ⇄ sshd（TCP 22）/etc/ssh/ssh_host_ed25519_key（サーバー）
~/.ssh/known_hosts（クライアント）		アルゴリズム交渉 → 鍵共有 → サーバーがホスト鍵で交換ハッシュ H に署名 → クライアントが known_hosts の公開鍵で検証 → 暗号化開始
ユーザー認証RFC 4252暗号化済みの経路上~/.ssh/id_ed25519 または ssh-agent（クライアント）
~/.ssh/authorized_keys（サーバー）		クライアントがセッション識別子を含むデータにユーザー秘密鍵で署名 → サーバーが authorized_keys の公開鍵で検証
コネクション層RFC 4254認証後のセッション~/.ssh/config・/etc/ssh/sshd_configシェル・コマンド実行・ポートフォワード（-L -R -D）をチャネルとして多重化

鍵ファイルの中身

公開鍵 id_ed25519.pub：1 行 3 フィールド

⟪ssh-ed25519⟫ AAAAC3NzaC1lZDI1NTE5AAAAIICs0g2weZhh4dhLtKRKd8Snoru8mXVH0iYNbsqPHJFp ⟪you@example.com⟫
フィールド中身説明
ssh-ed25519鍵の種類他に ecdsa-sha2-nistp256、ssh-rsa、sk-ssh-ed25519@openssh.com（FIDO セキュリティキー）など
AAAAC3Nz…鍵 blob の base64（68 文字）デコードすると 51 バイト：00 00 00 0b + "ssh-ed25519" + 00 00 00 20 + 公開鍵 32 バイト（RFC 8709 §4）。先頭が必ず AAAAC3NzaC1lZDI1NTE5AAAAI になるのはこのため
you@example.comコメント-C で指定した任意の文字列。認証には使われません（ssh-keygen -c で変更可）

秘密鍵 id_ed25519：openssh-key-v1 形式

        
見た目は PEM ですが中身は PKCS#8 ではなく、OpenSSH 独自の openssh-key-v1 形式です（仕様は OpenSSH 付属の PROTOCOL.key）。パスフレーズなしだと ciphername が none、ありだと aes256-ctr と KDF bcrypt になり、秘密鍵部分が暗号化されます。

        
"openssh-key-v1\0"          マジック
00000004 "none"             ciphername   （パスフレーズありなら "aes256-ctr"）
00000004 "none"             kdfname      （同 "bcrypt"）
00000000                    kdfoptions   （同 salt と rounds）
00000001                    鍵の個数
00000033 ⟪公開鍵 blob 51 B⟫    .pub と同じ blob
00000098 ⟪秘密セクション 152 B⟫ checkint×2・鍵種別・公開鍵・秘密鍵・コメント・padding

        
秘密鍵ファイルから公開鍵は復元できます：ssh-keygen -y -f ~/.ssh/id_ed25519 > id_ed25519.pub。逆（公開鍵 → 秘密鍵）はできません。

      


      
      

        
接続とホスト認証（鍵交換）

        
ユーザー認証より先に、サーバーの本人確認と暗号化が済みます。サーバーはホスト秘密鍵 /etc/ssh/ssh_host_ed25519_key で「この接続の交換ハッシュ H」に署名し、クライアントは ~/.ssh/known_hosts に保存したホスト公開鍵でそれを検証します。H にはこの接続でしか出てこない一時鍵が入るので、署名を使い回すことはできません。

OpenSSH の既定の鍵交換アルゴリズム（バージョン別）

        

          

            
バージョン既定で最優先の kex備考

            
              
OpenSSH 10.0 以降（2025-04）mlkem768x25519-sha256ML-KEM-768（FIPS 203）と X25519 のハイブリッド。10.1 からは、耐量子でない kex が選ばれると ** WARNING: connection is not using a post-quantum key exchange algorithm. と表示（WarnWeakCrypto）

              
OpenSSH 9.0〜9.9sntrup761x25519-sha512@openssh.comStreamlined NTRU Prime と X25519 のハイブリッド。9.9 で mlkem768x25519-sha256 が追加（既定ではない）

              
OpenSSH 8.9 以前curve25519-sha256X25519 の ECDH（RFC 8731）

            
          

        

        
どれも同じメッセージ（SSH_MSG_KEX_ECDH_INIT (30) / SSH_MSG_KEX_ECDH_REPLY (31)）でやり取りします。違うのは中身の大きさで、curve25519-sha256 では Q_C・Q_S は 32 バイトの X25519 公開鍵、mlkem768x25519-sha256 では Q_C = ML-KEM-768 公開鍵 1184 バイト ‖ X25519 公開鍵 32 バイト、Q_S = ML-KEM 暗号文 1088 バイト ‖ X25519 公開鍵 32 バイトになります。


        
known_hosts の書式

        
server.example.com ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIBEDErqZ2CAGW7Qa5VehKWuP8A/nse1EVt8vPduCPiHr
[git.example.com]:2222 ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAI…        # 22 以外のポートは [host]:port
⟪|1|FFrdmEesy6T53v8juoCrA1YcMH0=|jgsKpqc3dA1gvgjV9IA+gXPG/gE=⟫ ssh-ed25519 AAAAC3Nz…  # HashKnownHosts yes のときのホスト名ハッシュ
@cert-authority *.example.com ssh-ed25519 AAAAC3Nz…                  # ホスト証明書の CA を信頼する行

        
1 行 = 「ホスト名（カンマ区切り可）・鍵の種類・base64 の公開鍵 blob」。|1|salt|hash は HashKnownHosts yes（Debian/Ubuntu の /etc/ssh/ssh_config では有効）で書かれたもので、ホスト名を HMAC-SHA1 で隠しています。探すときは ssh-keygen -F server.example.com を使います。

      


      
      

        
ユーザー認証（publickey）

        
暗号化が始まった後、クライアントは「この公開鍵で認証したい」と申し出て、サーバーが authorized_keys に載っていると答えたら、セッション識別子（最初の鍵交換の H）を含むデータに秘密鍵で署名して送ります。署名対象にセッション固有の値が入るので、盗聴した署名を別の接続で再利用することはできません。

署名されるデータと、サーバーの検証

        
RFC 4252 §7 の publickey 方式では、署名対象は「セッション識別子 + 認証要求メッセージそのもの」です。OpenSSH 8.9 以降の組み合わせでは、サーバーが SSH_MSG_EXT_INFO で publickey-hostbound@openssh.com を通知すると、クライアントは publickey-hostbound-v00@openssh.com 方式を使い、サーバーのホスト公開鍵も署名対象に加えます（ssh-agent の転送先制限 ssh-add -h のため）。

        

          

            
メッセージ番号向き中身

            
              
SSH_MSG_SERVICE_REQUEST5c → s"ssh-userauth"

              
SSH_MSG_USERAUTH_REQUEST50c → sユーザー名・"ssh-connection"・方式名・（publickey なら）署名有無・アルゴリズム・公開鍵・署名

              
SSH_MSG_USERAUTH_FAILURE51s → c続けて使える方式の一覧（publickey,password）

              
SSH_MSG_USERAUTH_PK_OK60s → c「その公開鍵なら受け付ける。署名を送れ」

              
SSH_MSG_USERAUTH_SUCCESS52s → c認証成功

              
SSH_AGENTC_SIGN_REQUEST13ssh → agent公開鍵 blob・署名対象データ・flags（$SSH_AUTH_SOCK の UNIX ソケット経由）

              
SSH_AGENT_SIGN_RESPONSE14agent → ssh署名

失敗ケース：ホスト鍵の不一致・パーミッション・Permission denied

        
SSH のエラーは「どちらのマシンの、どのファイルが原因か」で直し方が決まります。ホスト鍵の不一致はクライアントの known_hosts、UNPROTECTED PRIVATE KEY FILE はクライアントの秘密鍵のモード、Permission denied (publickey) は多くの場合サーバー側の authorized_keys かそのディレクトリのモードです。

ファイルホストモード誰が読む / 書く

            
              
~/.ssh/id_ed25519client600（400 も可）ssh-keygen が作成、ssh / ssh-add が読む。group/other に権限があると無視される

              
~/.ssh/id_ed25519.pubclient644ssh-copy-id がサーバーへ送る

              
~/.ssh/known_hostsclient644初回接続時に ssh が追記、以後は照合。ssh-keygen -R で削除

              
~/.ssh/configclient600 推奨ssh が最初に読む（ssh -G host で最終値）

              
~/.ssh/authorized_keysserver600sshd がユーザー認証時に読む。StrictModes yes ならファイル・~/.ssh・ホームが他人に書き込み可だと拒否

              
/etc/ssh/ssh_host_*_keyserver600 rootインストール時に ssh-keygen -A 等で生成。sshd が鍵交換で H に署名

              
/etc/ssh/sshd_configserver644sshd が起動・再読込時に読む（sshd -t で構文検査）

            
          

        

      


      
      

        
sshd_config の重要な設定

        

          

            
設定OpenSSH の既定値意味・よく使う値

            
              
PubkeyAuthenticationyes公開鍵認証を許可

              
PasswordAuthenticationyes鍵を配り終えたら no にしてパスワード総当たりを止める

              
KbdInteractiveAuthenticationyesPAM 経由のパスワード入力もこちら。パスワードを止めるなら両方 no（8.7 で ChallengeResponseAuthentication から改名）

              
PermitRootLoginprohibit-passwordroot は鍵のみ許可。no で完全禁止

              
AuthorizedKeysFile.ssh/authorized_keys .ssh/authorized_keys2同梱の sshd_config は .ssh/authorized_keys のみに上書き。%h %u が使える

              
StrictModesyesホーム・~/.ssh・authorized_keys が他人に書き込み可なら拒否

              
MaxAuthTries61 接続での認証試行回数。鍵をたくさん agent に入れていると Too many authentication failures

              
AllowUsers / AllowGroups（なし）ログインできるユーザーを限定

              
Port / ListenAddress22 / 全アドレス待ち受け

              
HostKey/etc/ssh/ssh_host_*_key使うホスト鍵

~/.ssh/config とポートフォワード

        
Host bastion
    HostName bastion.example.com
    User alice
    IdentityFile ~/.ssh/id_ed25519
    IdentitiesOnly yes          # IdentityFile の鍵だけを提示する

Host app1
    HostName 10.0.1.23          # 踏み台の内側のアドレス

ssh app1 と打つと、bastion に SSH で入り、そこから 10.0.1.23:22 への TCP を中継させて、その上でもう一度 SSH（鍵交換・ホスト鍵確認・認証）をします。app1 のホスト鍵は手元の known_hosts に 10.0.1.23 として記録されます。最終的な設定値は ssh -G app1 で確認できます。

        

          

            
フラグ例何が起きるか

-Rssh -R 8080:localhost:3000 serverserver の localhost:8080 への接続を、手元の localhost:3000 へ中継（リモートフォワード）

              
-Dssh -D 1080 bastion手元に SOCKS プロキシ localhost:1080 を立て、接続先ごとに bastion から接続（ダイナミックフォワード）

              
-Jssh -J bastion deploy@10.0.1.23踏み台経由（ProxyJump）

              
-Nssh -N -L …リモートコマンドを実行しない（転送専用）

コマンド主なフラグ何が起きるか

ハマりどころ

        
ホスト鍵の警告で StrictHostKeyChecking no にしない。警告は MITM を検知した結果かもしれません。CI などで自動化するなら、事前に正しいホスト鍵を known_hosts に配っておくか、StrictHostKeyChecking accept-new（初回のみ自動追加・変更は拒否）を使います。

        
秘密鍵はモード 600。group/other に 1 ビットでも権限があると Permissions 0644 … are too open. で黙って無視され、結果として Permission denied (publickey) になります。Windows の OpenSSH では NTFS の ACL で同じ検査をします。

        
サーバー側の StrictModes。ホームディレクトリ・~/.ssh・authorized_keys が group/other 書き込み可だと、クライアントには理由が出ず Permission denied (publickey) だけが返ります。理由はサーバーのログ（Authentication refused: bad ownership or modes …）にしか出ません。

        
agent に鍵を入れすぎると Too many authentication failures。ssh は agent の鍵を順番に提示し、MaxAuthTries（既定 6）を超えると切断されます。~/.ssh/config で IdentityFile と IdentitiesOnly yes を指定します。

        
authorized_keys の 1 行が途中で折り返されている。コピー時に改行が入ると別の行として解釈されます。1 鍵 = 1 行です。ssh-copy-id を使うか、ssh-keygen -lf ~/.ssh/authorized_keys で全行が読めるか確認します。

        
フィンガープリントの形式違い。OpenSSH 6.8 以降は SHA256:（base64）、古い資料や他ツールは MD5:xx:xx:…（16 進）です。比べるときは ssh-keygen -l -E md5 -f で形式を揃えます。

        
ssh-agent のソケットの場所。OpenSSH 10.1 から ssh-agent と転送された agent のソケットは /tmp ではなく ~/.ssh/agent/ 配下に作られます。/tmp/ssh-* を前提にしたスクリプトは見直しが必要です。
