DNS 名前解決getaddrinfo() から権威サーバーまで、1 回の問い合わせを追いかける

curl https://www.example.com/ を実行すると、IP アドレスを得るまでに /etc/nsswitch.conf・/etc/hosts・/etc/resolv.conf、ローカルのスタブリゾルバ、キャッシュ DNS、そしてルート → TLD → 権威サーバーへの問い合わせが順に動きます。このページでは、その 1 回の名前解決を dig の出力と DNS メッセージのバイト列で追い、ゾーンファイル・キャッシュ・失敗時の status: までを実物で見ます。

全体像：1 回の名前解決で、誰が誰に何を聞くか

フルサービスリゾルバ

DNS メッセージの中身

問い合わせも応答も同じ形式のメッセージです。12 バイトのヘッダの後に Question / Answer / Authority / Additional の 4 セクションが続き、各セクションの件数はヘッダに入っています（RFC 1035 §4.1）。下のシーンでは dig が実際に送る 44 バイトのクエリと、60 バイトの応答を 1 バイトずつ分解します。

ヘッダのフラグとコード

フィールドビット意味dig の表示
ID16問い合わせ ID。応答はクエリと同じ ID を返す（送信元ポートと合わせてなりすまし対策）id: 41412
QR10 = 問い合わせ, 1 = 応答qr
OPCODE40 = QUERY（標準問い合わせ）, 4 = NOTIFY, 5 = UPDATEopcode: QUERY
AA1Authoritative Answer。権威サーバーが自分のゾーンから答えたaa
TC1TrunCation。UDP に収まらず切り詰めた → TCP で再問い合わせtc
RD1Recursion Desired。「最後まで調べて」（スタブ → リゾルバ）rd
RA1Recursion Available。このサーバーは再帰に応じるra
AD / CD1 / 1Authentic Data（DNSSEC 検証済み）/ Checking Disabled（検証しないで）。RFC 4035ad / cd
RCODE40 NOERROR, 1 FORMERR, 2 SERVFAIL, 3 NXDOMAIN, 4 NOTIMP, 5 REFUSEDstatus: NOERROR
QDCOUNT ほか16 × 4Question / Answer / Authority / Additional の件数QUERY: 1, ANSWER: 1, …
UDP・TCP・EDNS：DNS は通常 UDP/53 で、EDNS なしの UDP 応答は 512 バイトまでです（RFC 1035 §4.2.1）。EDNS(0)（RFC 6891）の OPT 疑似 RR で「この大きさまで受け取れる」と伝えると、それ以上の UDP 応答が可能になります。BIND 9.18 の dig や多くのリゾルバは既定で 1232 バイトを広告します。それでも収まらないと応答に TC が立ち、クライアントは TCP/53 で問い直します。TCP では各メッセージの前に 2 バイトの長さが付きます（RFC 1035 §4.2.2）。

キャッシュと TTL

フルサービスリゾルバは、受け取ったレコードを TTL（秒）の間キャッシュし、その間は権威サーバーに聞かずに答えます。キャッシュから返す応答の TTL は「残り時間」なので、同じ名前を 2 回 dig すると TTL が減って見えます。「存在しない」という答えも SOA の値に従ってキャッシュされます（ネガティブキャッシュ、RFC 2308）。

203.0.113.53 · 権威
経過 0 秒

; （空）
db.example.comserial 2026092801
www  3600 IN A 203.0.113.10
@    SOA … minimum 300
root@client01:~ — dig
ネガティブキャッシュの TTL：NXDOMAIN や NODATA の応答には Authority セクションにゾーンの SOA が付き、リゾルバはそれを「SOA の TTL」と「SOA の MINIMUM フィールド」の小さい方の秒数だけキャッシュします（RFC 2308 §5）。この例では min(3600, 300) = 300 秒です。新しいサブドメインを作る直前に一度引いてしまうと、最大でこの時間は「存在しない」と答えられ続けます。

DNSSEC：署名の連鎖（概要）

DNSSEC は各 RRset に署名（RRSIG）を付け、ゾーンの公開鍵（DNSKEY）のハッシュを親ゾーンに DS として登録することで、ルートから順に「この鍵は親が保証している」という連鎖を作ります（RFC 4033〜4035）。検証するのはフルサービスリゾルバで、ルートの鍵（トラストアンカー）だけを事前に持っています。

トラストアンカー（ルート KSK）
  └─ .            DNSKEY  ── RRSIG で自己署名
       └─ com.    DS      ── ルートの鍵で署名（RRSIG）
            └─ com.          DNSKEY  ── DS のハッシュと一致するか
                 └─ example.com.  DS      ── com. の鍵で署名
                      └─ example.com.  DNSKEY 257（KSK）/ 256（ZSK）
                           └─ www.example.com. A + RRSIG  ── ZSK で署名
レコード置かれる場所中身
DNSKEY各ゾーンの頂点公開鍵。flags 257 = KSK（鍵署名鍵）、256 = ZSK（ゾーン署名鍵）、protocol 3、アルゴリズム（13 = ECDSA P-256/SHA-256 など）
RRSIG署名した RRset と同じ名前対象タイプ・アルゴリズム・ラベル数・元の TTL・有効期限・開始時刻・鍵タグ・署名者名・署名値
DS親ゾーン（委任点）子の KSK の鍵タグ・アルゴリズム・ダイジェスト種別（2 = SHA-256）・ダイジェスト
NSEC / NSEC3各名前「この間には名前がない」ことの署名付き証明（NXDOMAIN の検証）

ad フラグは「リゾルバが DNSSEC で検証できた」ことを示します。+dnssec は OPT の DO ビットを立てて RRSIG を要求します。検証に失敗するとリゾルバは SERVFAIL を返し、+cd（Checking Disabled）を付けると検証をせずに答えを返すので、「DNSSEC のせいで引けないのか」を切り分けられます。BIND 付属の delv はローカルで検証を行い、結果を ; fully validated / ; unsigned answer などで表示します。

ハマりどころ

変更したのに反映されない：リゾルバは古い答えを TTL が切れるまで返し続けます。切り替え前に TTL を短く（例 300）しておき、元の TTL 分待ってから値を変えます。急ぐときはリゾルバ側で unbound-control flush / rndc flushname / resolvectl flush-caches。ブラウザや OS のキャッシュ、アプリ内キャッシュ（JVM の networkaddress.cache.ttl など）も別にあります。
SOA のシリアルを上げ忘れる：プライマリでゾーンを編集してもシリアルが増えないと、セカンダリはゾーン転送をしないため、NS によって答えが食い違います。
末尾のドット：ゾーンファイルで shops.example.net（ドットなし）と書くと $ORIGIN が付いて shops.example.net.example.com. になります。MX・NS・CNAME の値で特に起きやすい間違いです。
ゾーン頂点に CNAME は置けない：CNAME は同じ名前に他のデータを持てませんが（RFC 1034 §3.6.2、RFC 2181 §10.1）、頂点には必ず SOA と NS があります。CDN やロードバランサを頂点で使いたいときは、A/AAAA を直接書くか、DNS 事業者独自の ALIAS / ANAME / CNAME フラットニング、または HTTPS レコードを使います。
lame delegation：親ゾーンの NS に載っているのに、そのサーバーがゾーンを持っていない（REFUSED や aa なしの応答）状態です。リゾルバは別の NS に回るので「たまに遅い・たまに SERVFAIL」という症状になります。dig +norecurse @<各NS> example.com SOA で全 NS が aa 付きで同じシリアルを返すか確認します。
search ドメイン：/etc/resolv.conf の search corp.example.com と options ndots:N により、ドット数の少ない名前には検索ドメインが付けて先に問い合わせられます。Kubernetes の Pod（ndots:5）で外部名の解決が遅くなる典型的な原因です。
/etc/hosts が勝つ：hosts: files dns では /etc/hosts が先に引かれます。dig は NSS を通らず DNS だけを見るので、「dig では正しいのにアプリは違う IP に行く」ときは getent hosts で確認します。
