Web / HTTP · Cross-Origin Resource Sharing

CORSリクエストは届いている。止めているのはブラウザ

CORS は「サーバーがアクセスを拒否する仕組み」ではありません。ブラウザがクロスオリジンのリクエストに Origin ヘッダを付けて送り、 返ってきた Access-Control-Allow-Origin などのヘッダを見て、レスポンスを JavaScript に渡してよいかをブラウザ自身が判定する仕組みです。 このページでは、その判定がどこで・どのヘッダで行われるのかを、実際の HTTP メッセージとコンソールエラーで追います。

判定する場所ブラウザの Fetch 実装（CORS check）
ブラウザが送るOrigin / Access-Control-Request-Method / -Headers
サーバーが返すAccess-Control-Allow-Origin / -Credentials / -Methods / -Headers
仕様WHATWG Fetch Standard「CORS protocol」

オリジン = scheme + host + port

CORS の「クロス」はオリジン（origin）が違うことを指します。オリジンは URL の scheme・host・port の 3 つ組で、 path・query・fragment は含みません。3 つのうち 1 つでも違えば別オリジンです。

基準：このページ（document）の URL
schemehttps:// hostapp.example.com port(443) path?query/dashboard?tab=1
location.origin → "https://app.example.com"
cross-origin の fetch に付くヘッダ
GET /v1/items HTTP/1.1
Host: api.example.com
Origin: https://app.example.com
Sec-Fetch-Mode: cors
Sec-Fetch-Site: same-site
https://app.example.com/api/users SAME-ORIGIN path だけが違う。path・query はオリジンに含まれない
http://app.example.com/ CROSS-ORIGIN scheme が違う（https ≠ http）。暗黙の port も 443 ≠ 80
https://app.example.com:8443/ CROSS-ORIGIN port が違う（443 ≠ 8443）
https://api.example.com/ CROSS-ORIGIN host が違う。ただし登録可能ドメインが同じなので same-site
https://app.example.com:443/ SAME-ORIGIN https の既定 port は 443。明示しても同じオリジン
https://example.com/ CROSS-ORIGIN 親ドメインでも host が一致しなければ別オリジン
比較対象（基準 https://app.example.com）同一オリジン？same-site？理由
https://app.example.com/api/usersはいはいpath はオリジンに含まれない
https://app.example.com:443/はいはいhttps の既定 port 443 を明示しただけ
http://app.example.com/いいえいいえscheme が違う（same-site も scheme を比較する “schemeful same-site”）
https://app.example.com:8443/いいえはいport が違う（site は port を見ない）
https://api.example.com/いいえはいhost が違う。登録可能ドメイン example.com は同じ
https://api.example/（https://app.example から）いいえいいえ登録可能ドメインが app.example と api.example で別
same-origin と same-site は別物です。CORS が見るのは origin（scheme + host + port の完全一致）。 Cookie の SameSite 属性や Sec-Fetch-Site ヘッダが見るのは site（scheme + 登録可能ドメイン。Public Suffix List で判定）です。 https://app.example.com → https://api.example.com は「cross-origin だが same-site」になります。

「単純リクエスト」になる条件

Fetch Standard では「単純リクエスト」という用語は使わず、次の条件をすべて満たすリクエストはプリフライト（CORS-preflight request）を省略する、と定義されています（MDN では simple request と呼ばれます）。

項目プリフライトなしで送れる値プリフライトが必要になる例
メソッドCORS-safelisted method：GET / HEAD / POSTPUT, PATCH, DELETE
ヘッダCORS-safelisted request-header：Accept, Accept-Language, Content-Language, Content-Type（下記の値のみ）, Range（単一の bytes 範囲）Authorization, X-Requested-With, X-Api-Key など独自ヘッダ全般
Content-Typeapplication/x-www-form-urlencoded / multipart/form-data / text/plainapplication/json
値の長さ各値 128 バイト以下、safelisted ヘッダ値の合計 1024 バイト以下長すぎる Accept など
プリフライトが省略されるのは「このリクエストは HTML の <form> でも昔から送れたから、送ること自体は今さら防げない」という互換性上の理由です。 安全だから省略されるのではありません。単純リクエストはサーバーに届き、副作用（書き込み）も実行されます。

プリフライト（OPTIONS）

PUT や Content-Type: application/json、Authorization ヘッダを使うと、ブラウザは本リクエストの前に OPTIONS メソッドのプリフライトを送り、「このオリジンから、このメソッドとヘッダで送ってよいか」をサーバーに問い合わせます。 許可が返らなければ本リクエストは送信されません（単純リクエストとの大きな違い）。

    credentialsクロスオリジンで Cookie を送る？レスポンスを読むための条件
    
            
              
    'omit'送らない（Set-Cookie も無視）Access-Control-Allow-Origin が * またはリクエストの Origin と一致
    
              
    'same-origin'（既定）送らない（同一オリジンなら送る）同上
    
              
    'include'送る（Cookie の SameSite 等の条件を満たす場合）ACAO が Origin と完全一致（* 不可）かつ Access-Control-Allow-Credentials: true
    
                
          
    
        
    
        
    
          XMLHttpRequest では xhr.withCredentials = true が credentials: 'include' に相当します。
          資格情報付きモードでは Access-Control-Allow-Headers / -Methods / -Expose-Headers の * もワイルドカードではなく「* という名前」として扱われます。

    Chrome のエラー文 → 原因 → 直し方
    
        
    Chrome / Edge では Access to fetch at '<URL>' from origin '<Origin>' has been blocked by CORS policy: に続けて理由が表示されます（文言はバージョンで変わることがあります）。
    
        
    
          
    
            
    理由部分（Chrome）原因直し方（サーバー側）
    
            
              
    No 'Access-Control-Allow-Origin' header is present on the requested resource.レスポンスに ACAO がない。エラー応答（4xx/5xx）にだけ付いていないことも多い許可する Origin を返す。nginx は add_header … always
    
              
    Response to preflight request doesn't pass access control check: It does not have HTTP ok status.OPTIONS が 2xx 以外（401/404/405 など）OPTIONS を認証・ルーティングより前で 204 にする
    
              
    Request header field authorization is not allowed by Access-Control-Allow-Headers in preflight response.Access-Control-Allow-Headers に Authorization がない（* でも Authorization は許可されない）Access-Control-Allow-Headers: Authorization, Content-Type
    
              
    Method PUT is not allowed by Access-Control-Allow-Methods in preflight response.メソッドが許可リストにないAccess-Control-Allow-Methods に追加
    
              
    The value of the 'Access-Control-Allow-Origin' header in the response must not be the wildcard '*' when the request's credentials mode is 'include'.資格情報付きなのに *Origin を許可リストで照合して、その値を返す
    
              
    The value of the 'Access-Control-Allow-Credentials' header in the response is '' which must be 'true' when the request's credentials mode is 'include'.資格情報付きなのに ACAC がないAccess-Control-Allow-Credentials: true
    
                
          
    
        
    
        
    Firefox では Cross-Origin Request Blocked: The Same Origin Policy disallows reading the remote resource at <URL>. (Reason: CORS header 'Access-Control-Allow-Origin' missing). のように、Reason: の後に理由が出ます。
    
        
    
          CORS は CSRF 対策ではありません。CORS が止めるのは「レスポンスを読むこと」だけで、単純リクエスト（form 相当の POST）は Cookie 付きでサーバーに届き、処理されます。
          CSRF には Cookie の SameSite=Lax/Strict、CSRF トークン、サーバーでの Origin / Sec-Fetch-Site 検査を使います。
        
    
      
    

      
      
    
        
    ヘッダ早見表
    
        
    ブラウザが付けるリクエストヘッダ（JS からは設定不可）
    
        
    
          
    
            
    ヘッダいつ付く値の例
    
            
              
    Originクロスオリジンの CORS リクエスト、プリフライト、同一オリジンでも GET/HEAD 以外https://app.example（path なし。サンドボックス iframe などでは null）
    
              
    Access-Control-Request-MethodプリフライトのみPUT
    
              
    Access-Control-Request-Headersプリフライトのみ（safelisted でないヘッダがあるとき）authorization,content-type（小文字・ソート済み）
    
              
    Sec-Fetch-Mode / Sec-Fetch-SiteFetch Metadata（対応ブラウザ）cors / cross-site, same-site, same-origin, none
    
                
          
    
        
    
        
    サーバーが返すレスポンスヘッダ
    
        
    
          
    
            
    ヘッダ返す場所値と意味
    
            
              
    Access-Control-Allow-Originプリフライト応答 + 本レスポンスhttps://app.example（1 つだけ。カンマ区切りの複数指定は不可）または *
    
              
    Access-Control-Allow-Credentialsプリフライト応答 + 本レスポンスtrue のみ有効。資格情報付きモードで必須
    
              
    Access-Control-Allow-Methodsプリフライト応答GET, PUT, DELETE。safelisted method（GET/HEAD/POST）は書かなくても通る
    
              
    Access-Control-Allow-Headersプリフライト応答Authorization, Content-Type。* は資格情報なしのときだけワイルドカード、かつ Authorization は含まない
    
              
    Access-Control-Max-Ageプリフライト応答キャッシュ秒数。省略時 5 秒。上限は Chromium 7200 秒、Firefox 86400 秒
    
              
    Access-Control-Expose-Headers本レスポンスX-Request-Id, ETag。書かないと JS からは safelisted な応答ヘッダ（Content-Type 等）しか読めない
    
              
    VaryOrigin によって応答が変わるときVary: Origin。共有キャッシュ（CDN・プロキシ）が別 Origin 向けの応答を使い回さないように
    
                
          
    
        
    
      
    

      
      
    
        
    サーバー設定例
    
        
    どれも「許可するオリジンの一覧と照合し、一致したときだけその Origin を ACAO に返す」形にしています。Origin を無条件に反射する設定は避けてください（§4 のシーン最終ステップ）。
    
        
    map $http_origin $cors_origin {
    default                "";          # 空文字なら add_header は出力されない
    "https://app.example"  $http_origin;
    "https://admin.example" $http_origin;
}

server {
    listen 443 ssl;
    server_name api.example;

    location /v1/ {
        if ($request_method = OPTIONS) {
            add_header Access-Control-Allow-Origin      $cors_origin always;
            add_header Access-Control-Allow-Credentials "true" always;
            add_header Access-Control-Allow-Methods     "GET, POST, PUT, DELETE" always;
            add_header Access-Control-Allow-Headers     "Authorization, Content-Type" always;
            add_header Access-Control-Max-Age           600 always;
            add_header Vary                             Origin always;
            return 204;
        }
        # ⟪always⟫ がないと 4xx/5xx 応答に付かず、本当のエラーが CORS エラーに化ける
        add_header Access-Control-Allow-Origin      $cors_origin ⟪always⟫;
        add_header Access-Control-Allow-Credentials "true" always;
        add_header Vary                             Origin always;
        proxy_pass http://127.0.0.1:8080;
    }
}

    ハマりどころ
    
        
    
          
      
            
    • エラー応答に CORS ヘッダがない：アプリが 500 を返したとき、nginx の add_header（always なし）やフレームワークの例外ハンドラが ACAO を付けないと、コンソールには本当の原因ではなく CORS エラーが出ます。サーバーログを先に見ます。
      • 
            
    • OPTIONS に認証をかけている：プリフライトには Authorization も Cookie も付きません。認証ミドルウェアより前で OPTIONS を処理します。
      • 
            
    • ACAO を複数値にしている：Access-Control-Allow-Origin: https://a.example, https://b.example は無効。リクエストの Origin を許可リストと照合して 1 つ返します。
      • 
            
    • Origin を無条件に反射 + Allow-Credentials: true：任意のサイトがログイン中ユーザーのデータを読めます。部分一致（endsWith('example.com') → evilexample.com が通る）や正規表現のドット未エスケープにも注意。
      • 
            
    • Origin: null を許可しない：サンドボックス iframe や file:// から送られる null を許可すると、攻撃者も null を作れます。
      • 
            
    • Vary: Origin 忘れ：CDN が「https://app.example 向けの ACAO 付き応答」を他のオリジンに返し、別のオリジンで CORS エラーになる（あるいはその逆）。
      • 
            
    • レスポンスヘッダが読めない：res.headers.get('X-Request-Id') が null なのは CORS の仕様。Access-Control-Expose-Headers が必要です。
      • 
            
    • mode: 'no-cors' で「直した」つもり：レスポンスは type: "opaque"、status: 0、本文は読めません。エラーが消えるだけです。
      • 
            
    • クロスサイトの Cookie が送られない：credentials: 'include' でも、Cookie が SameSite=Lax や Strict だったり（Chrome は SameSite 未指定の Cookie を Lax として扱います）、ブラウザのサードパーティ Cookie 制限に当たると付きません。API を同じサイト（例 app.example.com と api.example.com）に置くのが確実です。
      • 
            
    • 開発時だけプロキシで回避：Vite の server.proxy などで同一オリジンに見せると CORS は発生しません。本番構成と差が出る点に注意します。
