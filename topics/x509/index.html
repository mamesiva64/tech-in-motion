X.509 証明書server.crt の中身を、ASN.1 と DER のバイト列まで全部読む

証明書は「公開鍵」と「その持ち主の名前（X.501 の識別名 DN）」と「使い道の制約（拡張）」を 1 つの TBSCertificate にまとめ、発行 CA が秘密鍵で署名した DER バイト列です。このページでは openssl x509 -text の各行が DER のどのバイトに対応し、どこを 1 バイト書き換えると検証のどこで落ちるかを、実際に生成した証明書（OpenSSL 3.5 で作成）で追いかけます。

ファイルserver.crt（PEM）/ server.der（DER）
中身tbsCertificate + signatureAlgorithm + signatureValue
読むコマンドopenssl x509 -in server.crt -noout -text
仕様ITU-T X.509 / X.501、RFC 5280、RFC 4514、X.690（DER）

全体像：証明書の構造

左が openssl x509 -in server.crt -noout -text の出力（抜粋）、右が RFC 5280 §4.1 の ASN.1 定義です。ステップごとに「表示の 1 行」と「ASN.1 のフィールド」を対応づけます。署名がかかっているのは tbsCertificate の DER バイト列全体で、外側の 2 つ（signatureAlgorithm と signatureValue）は署名の対象外です。

X.501 の識別名（DN）：Subject と Issuer の正体

X.509 は ITU-T の X.500 シリーズ（ディレクトリ）の一部です。そのうち X.501（The Directory: Models）が「名前」のモデル＝識別名 Distinguished Name（DN）を定義し、X.509 がその名前を使って証明書の形式を定義しています。証明書の subject と issuer はどちらも X.501 の Name 型で、RFC 5280 §4.1.2.4 がインターネット用のプロファイルを決めています。

表記の注意：「X.501 証明書」というものはありません。X.501 は名前のモデル、X.509 は証明書の形式です。X.500 ディレクトリでは DN がツリー上のエントリの住所（例：C=JP → O=Example Inc → CN=www.example.com）を表していたため、上位から順に並ぶ構造になっています。

エンコード：DER の TLV と PEM

証明書の実体は ASN.1 を DER（X.690 Distinguished Encoding Rules）で符号化したバイナリです。DER はすべての値を Tag・Length・Value の 3 つ組で表し、同じ値の符号化が 1 通りに決まる（署名対象として安定する）ように規則を絞っています。PEM は DER を base64 にして -----BEGIN CERTIFICATE----- 行で挟んだテキスト形式（RFC 7468）です。

拡張（X509v3 extensions）

v3 証明書の extensions は Extension の SEQUENCE です。各拡張は OID・critical フラグ・extnValue（中にさらに DER が入った OCTET STRING）の 3 つ組で、「この鍵は CA として使えるか」「どのホスト名に有効か」「失効はどこで確かめるか」といった検証ルールはすべてここに書かれています。

手元で試す

OpenSSL 3.x（本ページは 3.5.7 で確認）と xxd があれば再現できます。小さな CA を 1 つ作り、そこで署名したサーバー証明書を読んで、1 バイト改ざんまで試します。Windows の Git Bash では -subj "/C=…" がパス変換されるため、先に export MSYS_NO_PATHCONV=1 を実行してください。

mkdir -p ~/x509-lab && cd ~/x509-lab

# 1) 検証用の小さな CA（自己署名, P-384）
openssl req -x509 -newkey ec -pkeyopt ec_paramgen_curve:P-384 -noenc \
  -keyout ca.key -out ca.crt -days 365 \
  -subj "/C=JP/O=Example Trust/CN=Example Test CA"

# 2) サーバー鍵（P-256）と CSR
openssl req -new -newkey ec -pkeyopt ec_paramgen_curve:P-256 -noenc \
  -keyout server.key -out server.csr \
  -subj "/C=JP/ST=Tokyo/L=Chiyoda-ku/O=Example Inc/CN=www.example.com"

# 3) CA が署名（拡張はここで付ける）
cat > leaf.ext <<'EOF'
basicConstraints = critical, CA:FALSE
keyUsage         = critical, digitalSignature
extendedKeyUsage = serverAuth
subjectAltName   = DNS:www.example.com, DNS:example.com, IP:192.0.2.10
EOF
openssl x509 -req -in server.csr -CA ca.crt -CAkey ca.key -sha384 -days 90 \
  -extfile leaf.ext -out server.crt

# 4) 中身を読む
openssl x509 -in server.crt -noout -text
openssl x509 -in server.crt -noout -subject -issuer -dates -serial
openssl x509 -in server.crt -noout -subject -nameopt RFC2253
openssl x509 -in server.crt -noout -ext subjectAltName,basicConstraints,keyUsage
openssl x509 -in server.crt -noout -fingerprint -sha256

# 5) DER にして先頭バイトと TLV を見る
openssl x509 -in server.crt -outform der -out server.der
xxd server.der | head -4
openssl asn1parse -in server.crt -i | head -30

# 6) 検証：成功 / ホスト名違い / 期限切れ（120 日後の時刻で検証。GNU date の書式）
openssl verify -CAfile ca.crt -verify_hostname www.example.com server.crt
openssl verify -CAfile ca.crt -verify_hostname shop.example.com server.crt
openssl verify -CAfile ca.crt -attime "$(date -d '+120 days' +%s)" server.crt

# 7) SAN の "www.example.com" の l(0x6c) を 1(0x31) に 1 バイト改ざん → 署名検証失敗
xxd -p server.der | tr -d '\n' \
  | sed 's/820f7777772e6578616d706c652e636f6d/820f7777772e6578616d7031652e636f6d/' \
  | xxd -r -p > evil.der
cmp -l server.der evil.der                       # 1 バイトだけ違う
openssl x509 -in evil.der -inform der -out evil.crt
openssl x509 -in evil.crt -noout -ext subjectAltName   # DNS:www.examp1e.com
openssl verify -CAfile ca.crt evil.crt           # error 7: certificate signature failure

# 8) 署名を手で検証する（TBS を切り出して dgst で）
openssl asn1parse -in server.crt -strparse 4 -noout -out tbs.der
SIGOFF=$(openssl asn1parse -in server.crt | tail -1 | cut -d: -f1 | tr -d ' ')
openssl asn1parse -in server.crt -strparse "$SIGOFF" -noout -out sig.der
openssl x509 -in ca.crt -noout -pubkey > ca.pub
openssl dgst -sha384 -verify ca.pub -signature sig.der tbs.der   # Verified OK

ハマりどころ

CN にホスト名を書いても照合されない：ブラウザは SAN の dNSName／iPAddress だけで照合します（Chrome 58 以降、RFC 9525 は CN-ID を廃止）。SAN なしで CN だけの証明書は Chrome で NET::ERR_CERT_COMMON_NAME_INVALID です。一方 openssl verify -verify_hostname は SAN に DNS 名が 1 つも無いと CN にフォールバックするので、openssl では OK でもブラウザでは NG になり得ます。
DN の表示順と区切りはツールとバージョンで違う：OpenSSL 3.2 以降の既定は C=JP, O=…, CN=…、1.1.1 / 3.0 / 3.1 の既定（-nameopt oneline）は C = JP, O = …、RFC 4514 形式（-nameopt RFC2253、Java、LDAP）は CN=…,O=…,C=JP と逆順です。出力を grep／パースするスクリプトは -nameopt を明示してください。
フィンガープリントの既定は SHA-1：openssl x509 -fingerprint はダイジェスト未指定だと SHA-1 です。ピン留めや照合では -sha256 を付け、比較相手（ブラウザの証明書ビューア等）と同じアルゴリズムか確かめます。
PEM の中身が 1 枚とは限らない：fullchain.pem のように複数枚が連結されていても、openssl x509 -in は先頭の 1 枚だけを表示します。全部見るには openssl crl2pkcs7 -nocrl -certfile fullchain.pem | openssl pkcs7 -print_certs -noout を使います。
有効期間は短くなり続ける：CA/B Forum Ballot SC-081v3 により、公開 TLS 証明書の最大有効期間は 2026-03-15 から 200 日、2027-03-15 から 100 日、2029-03-15 から 47 日です。notAfter の監視（-checkend）と自動更新が前提になります。
OU は使えない：公開 TLS 証明書の Subject に OU を入れることは 2022-09-01 以降禁止されています（Ballot SC47v2）。社内 CA のテンプレートを流用すると CSR に残りがちです。
改ざん検出は「署名」だけが担う：openssl x509 -text や証明書ビューアは改ざんされた証明書も普通に表示します（パースと検証は別処理）。「表示できた＝正しい」ではありません。
