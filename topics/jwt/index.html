JWTJSON Web Token — header.payload.signature の正体

JWT は「署名付きの JSON」です。暗号化ではありません。誰がどの鍵で署名し、誰がどの鍵で検証するのか、そして改ざんされたトークンがどこで・なぜ弾かれるのかを、実際のバイト列とコマンドで追います。このページに出てくるトークン・ハッシュ・署名は、あなたのブラウザ上で WebCrypto により本当に計算しています（鍵はページを開くたびに生成）。

構造：3 つのパートを組み立てる

JWS Compact Serialization（RFC 7515 §7.1）の形です。BASE64URL(UTF8(header)) と BASE64URL(payload) を . でつないだ ASCII 文字列が署名対象（JWS Signing Input）になり、その署名を base64url して 3 つ目に付けます。ここでは共有シークレット方式の HS256（HMAC-SHA256）で、値はすべてこのブラウザで計算しています。

header (JSON)
{"alg":"HS256","typ":"JWT"}
payload (JSON · claims)
{
  "sub": "42",
  "name": "alice",
  "role": "user",
  "iat": 1790000000,
  "exp": 1790000900
}

base64url とは：通常の base64 の + を -、/ を _ に置き換え、末尾の = パディングを削った形式（RFC 4648 §5）です。URL やヘッダにそのまま載せられるようにするためで、暗号化ではありません。

署名と検証：秘密鍵はどこ、公開鍵はどこ

本番では RS256（RSA）や ES256（ECDSA P-256）、EdDSA などの公開鍵暗号を使うのが一般的です。署名できるのは秘密鍵を持つ認可サーバーだけで、検証側（API）は公開鍵しか持たないため、API が侵害されてもトークンは偽造できません。下のシーンの鍵ペア・JWK・署名は、ページ表示時にブラウザ内で生成した本物の RSA 2048bit です。

検証パイプライン：どのチェックで何が止まるか

「署名が正しいか」だけでは足りません。RFC 8725（JWT Best Current Practices）が求めるのは、アルゴリズムの固定、信頼できる鍵だけを使うこと、そして exp・iss・aud などのクレーム検証です。代表的な攻撃・失敗ケースを、API 内の検証パイプラインに流してみます。

    JWS（署名）と JWE（暗号化）

    一般に「JWT」と呼ばれるものの大半は JWS（3 パート：header.payload.signature）で、中身は読めます。中身も隠したい場合は JWE（RFC 7516、5 パート：header.encrypted_key.iv.ciphertext.tag）を使います。

    どのトークンが JWT か

    OIDC の ID トークンは必ず JWT。アクセストークンは JWT のこともランダム文字列（opaque）のこともあります。リフレッシュトークンは通常 opaque。詳しくは OAuth 2.0 / OIDC。

    b64url() { base64 | tr '+/' '-_' | tr -d '=\n'; }

HEADER=$(printf '%s' '{"alg":"HS256","typ":"JWT"}' | b64url)
PAYLOAD=$(printf '%s' "{\"sub\":\"42\",\"role\":\"user\",\"exp\":$(( $(date +%s) + 900 ))}" | b64url)
SECRET=$(openssl rand -base64 32)

SIG=$(printf '%s' "$HEADER.$PAYLOAD" | openssl dgst -sha256 -hmac "$SECRET" -binary | b64url)
TOKEN="$HEADER.$PAYLOAD.$SIG"
echo "$TOKEN"

    ハマりどころ

    payload は暗号化されていない。パスワード・個人情報・内部 ID の体系など、見られて困るものを入れない。DevTools やプロキシのログで誰でも読めます。
    alg を固定する。ヘッダの alg で検証方式を決める実装は、none や RS256→HS256 の混同攻撃（公開鍵の PEM 文字列を HMAC の鍵として使わせる）を許します。検証 API には必ず algorithms: ['RS256'] のような許可リストを渡します。
    exp は秒。NumericDate は UNIX 秒です。JavaScript の Date.now() はミリ秒なので Math.floor(Date.now() / 1000)。ミリ秒を入れると 5 万年先まで有効なトークンになります。
    aud と iss を検証する。同じ認可サーバーが発行した「別 API 向け」のトークンでも署名は正しいので、aud を見ないと流用されます。
    失効できない。JWT はステートレスなので、発行後に取り消すには jti の denylist など追加の仕組みが要ります。アクセストークンは 5〜15 分程度と短くし、リフレッシュトークン（サーバー側で失効可能）と組み合わせるのが定石です。
    HS256 の弱いシークレット。トークン 1 つあればオフラインで総当たりできます。32 バイト以上のランダム値を使い、複数サービスで検証するなら非対称鍵（RS256 / ES256 / EdDSA）へ。
    ES256 の署名形式。openssl dgst -sign の ECDSA 署名は ASN.1 DER ですが、JWS は 64 バイトの R‖S 連結です。手で作るときは変換が必要です。
    保存場所。localStorage は XSS で抜かれます。HttpOnly; Secure; SameSite の Cookie に入れると JS から読めない代わりに CSRF 対策が必要です。SPA では BFF（Backend for Frontend）パターンも選択肢です。
    ヘッダサイズ。クレームを詰め込むとトークンが数 KB になり、プロキシのヘッダ上限（例：nginx の large_client_header_buffers）に当たって 400 / 431 になることがあります。
