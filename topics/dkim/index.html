Mail · DKIM / SPF / DMARC

DKIM (+SPF/DMARC)送信 MTA が署名し、受信 MTA が DNS の公開鍵で検証する

DKIM は「メールのどのヘッダと本文を、どのドメインの鍵で署名したか」を DKIM-Signature ヘッダに書き込む仕組みです。このページでは Postfix + OpenDKIM での鍵生成から、bh= と b= の計算、受信側での検証、改ざんで失敗する瞬間、そして SPF / DMARC との役割分担までを、実際のヘッダ・DNS レコード・コマンド出力で追います。ページ内の bh= と署名検証は、ブラウザの WebCrypto で実際に計算しています。

署名する場所送信側 MTA（Postfix → OpenDKIM milter）
/etc/opendkim/keys/example.com/sel1.private
検証する場所受信側 MTA（mx.example.net）が sel1._domainkey.example.com の TXT を引く
署名の対象h= に列挙したヘッダ + 本文ハッシュ bh= → 署名値 b=
仕様DKIM RFC 6376 / 8301 / 8463
SPF RFC 7208 · DMARC RFC 9989（旧 7489）

全体像：鍵はどこに置かれるか

DKIM の登場人物は 3 つです。送信側 MTA（Postfix と、milter として動く OpenDKIM）は秘密鍵を持ち、権威 DNS は公開鍵を TXT レコードで配り、受信側 MTA はメールが届くたびに DNS から公開鍵を取って検証します。秘密鍵が送信側ホストの外に出ることはなく、受信側は事前の鍵交換なしに検証できます。

DKIM-Signature ヘッダの中身

このページの例で送信側が付けた DKIM-Signature の全文です。b= は 2048bit RSA の署名（256 バイト）を base64 にした 344 文字で、途中の改行とタブは「折り返し（folding）」です。値は下のシーンで実際に検証できる本物です（鍵はこのページ用に生成したデモ鍵で、秘密鍵は公開していません）。

	bh=bo8O1PQAIkYltLnLg/rfWUvvkQPYwAOFn0pcjkhn8qc=;

タグ一覧（RFC 6376 §3.5）

タグ必須この例の値意味・注意
v=必須1バージョン。常に 1
a=必須rsa-sha256署名アルゴリズム。rsa-sha1 は RFC 8301 で署名にも検証にも使ってはならない（MUST NOT）。ed25519-sha256 は RFC 8463
c=任意relaxed/relaxed正規化「ヘッダ/本文」。省略時 simple/simple。c=relaxed だけなら本文は simple
d=必須example.com署名ドメイン（SDID）。公開鍵の場所と、DMARC の DKIM アラインメントに使われる
s=必須sel1セレクタ。公開鍵は <s>._domainkey.<d> の TXT
t=推奨1790558103署名時刻（UNIX 秒）。date -u -d @1790558103 → 2026-09-28 01:15:03 UTC
x=任意（なし）有効期限（UNIX 秒）。OpenDKIM では SignatureTTL を設定したときだけ付く
h=必須From:To:Subject:Date:Message-ID:From署名対象のヘッダ名（順序どおりに連結）。From は必須。存在しない名前を書くと「空」として署名され、後から追加されると検証が壊れる（オーバーサイン）
bh=必須bo8O1PQA…8qc=正規化した本文の SHA-256 を base64（44 文字）
b=必須OjpufJm2…ZvQ==署名値の base64。計算時は b= の値を空にした自分自身も署名対象に含める
l=任意（なし）本文の先頭 l オクテットだけを署名対象にする。後ろへの追記を許してしまう（→ 改ざんケース）
i=任意（なし）AUID。d= と同じかそのサブドメイン（例 @example.com）
q=任意（なし）鍵の取得方法。既定かつ唯一の定義値は dns/txt
z=任意（なし）署名時のヘッダ値のコピー（診断用）

公開鍵レコードのタグ（RFC 6376 §3.6.1）

タグ例意味

h=sha256受け入れるハッシュ。省略時はすべて

p=MIIBIjANBgkqhkiG9w0BAQEFAAOCAQ8AMIIBCgKCAQEA…公開鍵（必須）。RSA は SubjectPublicKeyInfo（DER）の base64。空にすると失効
t=y / sy＝テスト中、s＝i= のドメインが d= と完全一致すること

正規化（canonicalization）の 2 方式

メールは経路上で空白や折り返しが変わることがあります。正規化は「ハッシュを取る前に揃える」規則で、c=ヘッダ/本文 の組で指定します。

方式ヘッダ本文
simple一切変更しない（大文字小文字・空白・折り返しもそのまま）末尾の空行を削除（空本文は CRLF 1 つ）。それ以外は変更しない
relaxedヘッダ名を小文字化、折り返しの CRLF を除去、連続する空白（WSP）を 1 つの SP に、値の末尾とコロン前後の空白を削除行末の空白を削除、行内の連続空白を 1 つの SP に、末尾の空行を削除（空本文は空文字列）
空本文のハッシュは実物で覚えておくと便利です。simple の空本文（CRLF）は bh=frcCV1k9oG9oKj3dpUqdJg1PxRT2RSN/XKdLCPjaYaY=、relaxed の空本文（0 バイト）は bh=47DEQpj8HBSa+/TImW+5JCeuQeRkm5NMpJWZG3hSuFU= です。

DKIM の検証は 2 段階です。まず本文ハッシュ bh= を比べ、一致したらヘッダの署名 b= を検証します（RFC 6376 §6.1.3）。どちらで失敗したかで、原因が「本文が変わった」のか「署名対象のヘッダが変わった」のかが分かります。下のシーンの値はすべてページ上で再計算・再検証した結果です。

SPF と DMARC：3 つの検査が見るもの

DKIM が保証するのは「d= のドメインが、このヘッダと本文に署名した」ことだけで、利用者が目にする From: のドメインと一致しているかは見ません。SPF は SMTP の エンベロープ（MAIL FROM）のドメインに対して送信元 IP を検査します。そして DMARC が「SPF か DKIM のどちらかが pass し、かつそのドメインがヘッダ From とアラインしているか」を判定し、失敗時の扱い（p=）を From ドメインの所有者が宣言します。

検査対象の識別子引く DNS 名比べるもの転送されると

アラインメント（adkim / aspf）

From のドメイン比べる相手r（relaxed・既定）s（strict）
example.comDKIM d=example.com一致一致
example.comDKIM d=mail.example.com一致（組織ドメインが同じ）不一致

この例の adkim=s; aspf=r は「DKIM は d= が From と完全一致したときだけ、SPF は同じ組織ドメインなら認める」という意味です。組織ドメインの決め方は、RFC 7489 では Public Suffix List、RFC 9989 では DNS を親方向にたどる DNS Tree Walk に変わりました。

OpenDKIM がなくても、openssl と printf だけで DKIM の計算を再現できます（GNU coreutils の base64 -w0 を使います）。bh= は決定的なので、このページと同じ値になります。b= は鍵が違うので値は変わりますが、自分の鍵で署名・検証が通ることを確認できます。

$ BH=$(openssl dgst -sha256 -binary body.c | base64); echo "$BH"

ハマりどころ

TXT の 255 文字分割：TXT の 1 つの文字列（character-string）は最大 255 オクテットです（RFC 1035 §3.3）。2048bit 鍵の p= は 392 文字あるので、"…" "…" のように複数の文字列に分けて登録し、受信側はそれを間に何も挟まずに連結します（RFC 6376 §3.6.2.2）。DNS 管理画面によっては分割を自動でしない・引用符ごと値に入ってしまうことがあるので、dig +short TXT で "v=DKIM1; …" "…" の形になっているか確認します。
転送で SPF が壊れる：転送サーバは元の MAIL FROM のまま自分の IP から再送するため、SPF は fail になります。DKIM は内容が変わらなければ残るので、DMARC は DKIM のアラインメントで pass できます。転送側で SRS（Sender Rewriting Scheme）により MAIL FROM を書き換える方法もあります。
メーリングリストで DKIM が壊れる：件名への [list] 付加やフッタ追加で b= / bh= が不一致になります。対策は ML 側の From 書き換え（Mailman の DMARC 対策設定）、ARC（RFC 8617）による経路上の認証結果の引き継ぎ、または ML が自ドメインで再署名することです。
セレクタのローテーション：(1) 新しいセレクタ sel2 の TXT を先に公開 → (2) TTL 以上待ってから署名を sel2 に切り替え → (3) 配送中・再送待ちのメールのために旧 sel1 をしばらく残す → (4) sel1 を p= 空（失効）にしてから削除、の順にします。いきなり消すと、配送途中のメールが検証できなくなります。
秘密鍵のパーミッション：OpenDKIM は既定（RequireSafeKeys yes）で、他のユーザーが読み書きできる秘密鍵ファイルを安全でないとみなし、ログに key data is not secure を出して使いません。chown opendkim:opendkim と chmod 600 にします。
署名される/されないの判定：Mode sv の OpenDKIM は、接続元が InternalHosts（既定 127.0.0.1 のみ）に含まれるメールに署名し、それ以外は検証します。社内ネットワークからのメールに署名されないときは、まず InternalHosts を確認します。
鍵長とアルゴリズム：RFC 8301 により rsa-sha1 は使えず、署名者は 1024bit 以上（推奨 2048bit 以上）の RSA 鍵を使います。Ed25519（RFC 8463）は受信側の対応にばらつきがあるため、使う場合は RSA 署名と併用する（1 通に 2 つの DKIM-Signature を付ける）運用が一般的です。
